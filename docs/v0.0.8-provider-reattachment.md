# v0.0.8 — Provider Reattachment Semantics

## Goal

Make an in-flight provider invocation recoverable after coordinator restart without requiring a provider-assigned job ID to have been persisted before the crash.

## Deterministic reattachment key

A reattachable runner must advertise `provider.reattachment.v1` before the original physical authorization is created.

General Execution derives a client-generated `ProviderReattachmentKey` from the exact physical authorization and runner capabilities. The same key can later be reconstructed from the recovered lease plus the same runner capabilities.

A reattachable provider adapter is expected to pass `provider_key` to the provider as its idempotency / lookup key during the original submit. This removes the crash window between provider acceptance and local persistence of a provider-assigned job identifier.

Reattachment cannot be retrofitted by changing runner capabilities after dispatch: that changes the runner capability digest and breaks the original authorization binding.

## Status probe

`ProviderStatusProbe` contains only recovery identity:

- source durable-head digest;
- source snapshot digest;
- exact recovered lease;
- deterministic reattachment key.

It contains no workload objective, input payload, or instruction to start work. A status probe is therefore not a dispatch request.

## Provider status observations

Three statuses exist:

- `running` — the provider reports that the original invocation is still active;
- `not_found` — the provider cannot currently locate the invocation;
- `terminal` — the provider returns a complete v0.0.3 `PhysicalObservation` for the original authorization.

`running` produces disposition `keep_running`.

`not_found` produces disposition `remain_unknown`. It does **not** release capacity, authorize retry, create a failure result, or imply that the original provider work never existed.

`terminal` is admitted through the existing physical-outcome protocol. Only after that admission can the resulting `PhysicalOutcomeBundle` be passed to v0.0.7 reconciliation.

## Exact binding

A status observation must reproduce the probe digest, reattachment-key digest, and provider key. A terminal physical observation must also bind to the recovered authorization ID and invocation ID; then normal physical-outcome admission rechecks the full ExecutionSpec / registry / dispatch plan / Session / runner / authorization context.

## Authority boundary

Provider polling reports state. It does not create execution authority, capacity authority, evidence-verification authority, integration authority, or release authority.

A provider status of `not_found` is intentionally inconclusive.

## Conformance bank

The v0.0.8 tests cover deterministic pre-dispatch/post-restart key reconstruction, explicit capability gating, deterministic probes, running and not-found preservation, terminal outcome admission into v0.0.7, foreign-observation rejection, probe/key mismatch rejection, status-shape constraints, recovered-lease mismatch, no retroactive capability upgrade, and bounded detail-digest validation.

## Next boundary

After the stacked v0.0.5-v0.0.8 line is admitted, the next high-value milestone is a **concrete reattachable provider adapter** that actually submits and queries a provider using the client-generated key while preserving these protocol semantics.
