# v0.0.14 — Cold Lifecycle Settlement Integration

## Goal

Join the cold physical-recovery stack and v0.0.13 durable logical Session settlement without erasing the authority boundary between them.

v0.0.14 proves that a completed provider result can survive cold coordinator recovery, physical admission, capacity reconciliation, another restart boundary, and only then be explicitly submitted into the durable logical Session state.

## Four durable stores

The reference lifecycle uses four distinct filesystem-backed SQLite stores:

1. logical Session settlement store;
2. recovery-context store;
3. canonical capacity-head store;
4. provider identity/status registry.

The reference persistence order is:

```text
running Session
  -> recovery context
  -> capacity head
  -> provider identity
```

The running logical Session is therefore durable before physical work becomes externally recoverable.

## Preparation

`prepare_reference_cold_lifecycle(...)` constructs one authorized reference attempt and persists the four stores in the order above.

The resulting `LifecyclePreparationReceipt` binds the Session ID, running Session record digest, recovery context, anchor capacity head, provider key and deterministic provider job identity.

## Cold physical settlement

`resume_reference_completed_physical_settlement(...)` receives only the four filesystem paths.

It cold-bootstraps the execution context, verifies the exact durable Session is still `running`, reattaches the provider, records a bounded reference completion, admits the terminal physical outcome, and performs canonical capacity reconciliation.

After this operation:

```text
physical state = settled_terminal_reconciliation
logical Session = running
```

The completed `ResultEnvelope` is available as durable provider evidence, but the Session settlement store remains unchanged.

This is an executable proof of:

```text
physical completion != logical result submission
```

## Explicit logical settlement after another restart

`settle_reference_reconciled_result(...)` is a separate explicit operation.

It does not trust a result object retained from the physical-settlement call. Instead it reconstructs the evidence from durable stores:

```text
recovery context anchor
  + provider terminal observation
  + canonical physical reconciliation release
  -> re-admitted PhysicalOutcomeBundle
  -> exact ResultEnvelope
```

The reconstructed outcome digest must match the v0.0.12 canonical physical assessment. Only then does the caller-authorized operation invoke v0.0.13 Session settlement.

The first commit changes the durable logical state to `result_submitted`. Exact replay after lost acknowledgement is idempotent.

## Lifecycle assessment

`assess_reference_logical_lifecycle(...)` derives one of four states from stores only:

- `physical_pending_session_running`;
- `physical_settled_session_running`;
- `logical_result_submitted`;
- `logical_revoked`.

A terminal logical Session before the integrated physical lifecycle is settled is treated as an integrity failure in the reference lifecycle.

When the state is `logical_result_submitted`, the persisted logical result must equal the result reconstructed from the canonical reconciled physical outcome.

## Revocation race

The explicit logical authority remains caller-controlled. A caller may revoke the still-running Session after physical reconciliation instead of submitting the recovered result.

Once `revoked` is durable, later result settlement conflicts. Once `result_submitted` is durable, revocation conflicts. v0.0.13 therefore remains the single terminal-state authority for the logical Session.

## Lost acknowledgement

Two distinct lost-ack boundaries are now recoverable:

1. physical reconciliation committed but acknowledgement lost — v0.0.12 reconstructs `settled_terminal_reconciliation`;
2. logical Session result settlement committed but acknowledgement lost — v0.0.13 exact replay returns an idempotent terminal receipt.

v0.0.14 joins both into one cold lifecycle without conflating their states.

## Conformance bank

The v0.0.14 tests cover durable running Session preparation, cold completed physical reconciliation without logical submission, explicit durable post-reconciliation result settlement, lost-ack logical replay, premature settlement rejection, missing durable Session rejection, revocation winning over later result settlement, logical-row corruption, distinct four-store enforcement, and deterministic full lifecycle reproduction across fresh paths.

## Authority boundary

General Execution persists and reconstructs execution mechanics. It still does not verify application-domain correctness, choose whether a completed result should be accepted, integrate changes, or approve release.

## Admission boundary

v0.0.14 remains stacked above the v0.0.5-v0.0.13 candidate line. Targeted lifecycle evidence does not substitute for the full historical repository regression; canonical `main` remains unchanged.

## Next boundary

The next question is no longer whether a single completed attempt can survive cold restart end to end; v0.0.14 provides that reference proof. The next highest-value work is **retry/cancellation lifecycle integration and multi-session concurrency under the same durable stores**, followed by a full-stack regression in a complete runner environment. Those gates determine whether further protocol code has meaningful value or whether the implementation has reached its current structural ceiling.
