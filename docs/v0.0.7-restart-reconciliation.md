# v0.0.7 — Post-Restart Provider Reconciliation

## Goal

Resolve a recovered `in_flight_unknown` physical lease using later provider evidence without inventing an outcome, duplicating canonical execution, or losing the evidence that caused capacity to be released.

## Two-phase protocol

Reconciliation is intentionally split into two layers.

1. `prepare_restart_reconciliation(...)` reconstructs and verifies a deterministic candidate from the exact durable snapshot, execution context, recovered lease, and admitted physical outcome.
2. `SQLiteDurableHeadStore.commit_reconciliation(...)` atomically stores the reconciliation record and advances the canonical durable head.

Storage does not decide whether provider evidence is valid. The candidate is self-verifying and reruns the physical-outcome verification before persistence.

## Exact binding

A `ReconciliationRecord` binds the runner capability digest, logical Session, attempt, ExecutionSpec, dispatch plan, registry, source durable head, recovered lease, physical authorization, invocation, provider outcome, receipt, capacity release, and successor durable head.

The verifier requires one exact chain:

```text
recovered in_flight_unknown lease
  -> exact physical authorization
  -> exact admitted provider outcome
  -> exact receipt
  -> exact capacity release
  -> exact successor RunnerCapacityState
  -> exact successor DurableCapacityHead
```

Changing the Session context, provider outcome, receipt, release, lease, or durable snapshots invalidates the candidate.

## Atomic reconciliation persistence

SQLite store schema v2 adds one canonical reconciliation row per `(runner_id, authorization_id)`.

The durable-head update and reconciliation-record insert occur in the same `BEGIN IMMEDIATE` transaction. The transaction verifies the exact successor head and record before commit.

This removes the crash gap where capacity could otherwise be released while the provider evidence that justified the release was forgotten.

## Conflict and replay semantics

Two different reconciliations for one physical authorization cannot both become canonical.

A stale source durable head cannot reconcile unless the same reconciliation record was already committed. Exact replay after a lost acknowledgement is idempotent, including when later valid durable heads have already advanced.

## Completed versus failed outcomes

A terminal failed transport outcome releases the recovered lease and preserves v0.0.3 retry lineage, so a later physical retry may reserve capacity normally.

A completed provider outcome also releases capacity, but reconciliation does not silently mutate the logical Session into `result_submitted`. Result submission remains an explicit protocol action. A completed physical attempt is still not a retry source.

## Store migration

The reference SQLite adapter migrates the v0.0.6 store metadata from `ge.sqlite-durable-head-store.v1` to v2 transactionally and creates the reconciliation table without replacing existing durable heads.

## Conformance bank

The repository includes targeted tests for failed and completed reconciliation, retry lineage, foreign authorization rejection, record tamper detection, changed Session context, changed provider outcome, atomic record/head persistence, lost-ack idempotency, conflicting outcomes for one authorization, stale source heads, replay after later head advancement, v1-to-v2 store migration, and persistence across reopen.

## Boundary

Reconciliation consumes already-admitted provider evidence. It does not verify domain correctness, integrate results, release software, or grant Build Colony verification authority.

## Next boundary

After this stacked candidate is admitted, the next high-value boundary is durable logical-session/result recovery: ensure a completed reconciled physical outcome can survive another coordinator restart before logical result submission without being forgotten or double-submitted.
