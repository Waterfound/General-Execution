# v0.0.13 — Durable Logical Session Settlement

## Goal

Make the logical `ExecutionSession` terminal state durable and idempotent without collapsing physical completion, application verification, or result submission into the same authority layer.

The v0.0.12 stack can recover physical work, provider terminal evidence, and capacity reconciliation across cold restart and lost acknowledgements. Before v0.0.13, however, `submit_result(...)` and `revoke_session(...)` still returned only new in-memory Session objects.

## Durable Session record

`DurableSessionRecord` binds:

- the exact original running `ExecutionSession`;
- the exact current Session state;
- the complete `ResultEnvelope` only when the current state is `result_submitted`.

The allowed one-way state graph is:

```text
running -> result_submitted
       \-> revoked
```

No terminal state can return to `running`, and `result_submitted` cannot be replaced by a different result or by revocation.

The record reconstructs terminal states using the existing Session functions:

- `submit_result(source_session, result)` for result settlement;
- `revoke_session(source_session)` for revocation.

The persistence layer therefore does not invent new logical Session semantics.

## Explicit authority

The durable store never observes a physical outcome and automatically submits its result.

A caller must explicitly invoke:

```text
SQLiteSessionSettlementStore.submit_result(source_session, result)
```

or:

```text
SQLiteSessionSettlementStore.revoke(source_session)
```

This operation persists an already-authorized logical transition. It does not decide whether the result is application-correct, verified, integrable, or releasable.

The boundary remains:

```text
physical completion != logical result submission
```

## Running registration

Before terminal settlement, the exact running Session must already exist durably through `register_running(...)`.

This gives restart recovery an explicit pre-terminal state and prevents a result or revocation from materializing in storage without a durable source Session.

Exact repeated registration is idempotent. A different Session binding that happens to produce the same `session_id` is rejected.

## Atomic settlement

`SQLiteSessionSettlementStore` uses a filesystem-backed SQLite row per logical Session and `BEGIN IMMEDIATE` transactions.

When the current durable state is `running`, settlement performs a compare-and-swap style update from the exact stored record digest to one terminal record and verifies the committed row inside the same transaction.

After a successful terminal commit:

- exact replay returns an idempotent receipt;
- a different result conflicts;
- result submission after revocation conflicts;
- revocation after result submission conflicts.

Concurrent writers therefore converge on at most one logical terminal state.

## Lost acknowledgement

If the terminal database update committed but the caller lost the acknowledgement, repeating the exact operation is safe.

The store recognizes that the exact target record is already canonical and returns `SessionSettlementReceipt(idempotent=True)` without creating another transition.

This is the logical-Session analogue of the durable physical/reconciliation lost-ack behavior established earlier in the stack.

## Serialization and integrity

Session records use canonical JSON and strict schema checks for both `ExecutionSession` and `ResultEnvelope` payloads.

Stored metadata binds:

- `session_id`;
- source Session digest;
- current Session digest;
- current state;
- complete record digest.

A mismatch between row metadata and canonical payload is an integrity failure.

The reference store uses WAL and `synchronous=FULL`; `:memory:` is rejected because the milestone specifically targets restart durability.

## Conformance bank

The v0.0.13 tests cover running registration/reopen, idempotent registration, durable result submission, lost-ack result replay, conflicting result rejection, durable/idempotent revocation, result-after-revocation rejection, revocation-after-result rejection, concurrent identical result settlement, concurrent result-versus-revocation single-winner behavior, missing durable source rejection, same-session-ID binding substitution rejection, canonical record round-trip, nested schema rejection, store metadata corruption, row digest corruption, and filesystem-only storage.

## Admission boundary

v0.0.13 remains stacked above the v0.0.5-v0.0.12 candidate line. Targeted settlement evidence does not substitute for the full historical repository regression, and canonical `main` remains unchanged.

## Next boundary

The next highest-value milestone is **full cold lifecycle settlement integration**: register the running Session before physical work becomes recoverable, carry its store through cold bootstrap and capacity reconciliation, then explicitly persist `result_submitted` after a recovered completed outcome. Cut points immediately before and after logical settlement must prove `running` versus `result_submitted` without ambiguity.
