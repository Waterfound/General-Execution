# v0.0.6 — SQLite Durable Head Persistence

## Goal

Provide the first concrete persistence adapter for the v0.0.5 durable-head protocol without moving execution or verification authority into storage.

## Storage model

`SQLiteDurableHeadStore` keeps one canonical durable head per `runner_id`. Each row stores the exact head digest, generation, snapshot digest, and canonical serialized snapshot.

SQLite is used only as a durability and atomicity substrate. The stored snapshot must still pass the existing v0.0.5 typed decoding, capacity replay, runner binding, head binding, and successor verification.

## Atomic compare-and-swap

Writers call `compare_and_swap(snapshot, runner, expected_head_digest=...)`.

The adapter opens a `BEGIN IMMEDIATE` transaction, reads the current canonical row, verifies the expected head, verifies the candidate relationship, writes the new row, rereads and validates the exact candidate inside the same transaction, and only then commits.

A later writer that began from an older head is rejected as stale. SQLite serializes the write transaction; General Execution still defines the head-transition rules.

## Durability

Connections use WAL journaling and `synchronous=FULL`. Reopening a new store instance must reconstruct the same canonical durable snapshot through the v0.0.5 loader.

The adapter intentionally rejects `:memory:` because the milestone is about restart durability.

## Idempotent commit replay

If a caller lost the acknowledgement after a successful commit, it may retry the exact already-canonical snapshot while expecting that same current head. The adapter returns an idempotent `PersistenceCommitReceipt` and does not create another head transition.

## Integrity boundaries

The adapter rejects:

- an absent head when a previous head was expected;
- a first stored snapshot that depends on an unstored durable predecessor;
- a stale expected head;
- a candidate that is not a valid durable successor;
- stored metadata that disagrees with the serialized snapshot;
- a changed runner capability digest under an existing runner ID;
- unsupported store schema versions.

Different runner IDs have independent canonical rows.

## Conformance bank

The repository includes SQLite tests for restart persistence, successor commits, two-writer compare-and-swap, idempotent replay, stale-head rejection, predecessor requirements, rollback rejection, runner-capability binding, independent runner heads, stored metadata consistency, store schema checks, initial expected-head handling, and receipt schema validation.

An isolated SQLite harness also confirmed one-winner concurrent CAS, stale-writer rejection, idempotent replay, and persistence after close/reopen without GitHub Actions.

## Boundary

Persistence stores protocol state. It does not decide whether a workload is valid, whether provider evidence is correct, whether a result is verified, or whether anything should be integrated or released.

## Next boundary

After the v0.0.5 full regression and the stacked v0.0.6 candidate are admitted, the next high-value milestone is recovery reconciliation between a persisted `in_flight_unknown` lease and concrete provider evidence after restart.
