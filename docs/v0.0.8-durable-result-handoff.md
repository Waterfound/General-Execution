# v0.0.8 — Durable Logical Result Handoff

## Goal

Close the crash gap between a completed post-restart physical reconciliation and the explicit logical `submit_result` transition.

A provider result that has already been reconciled must not disappear if the coordinator restarts before logical submission, and a logical result that has already been submitted must not be submitted a second time because its acknowledgement was lost.

## Three durable stages

The protocol distinguishes three states:

```text
completed physical reconciliation
  -> PendingLogicalResult
  -> explicit submit_result(...)
  -> LogicalResultSubmission
```

The existing `submit_result` function remains the authority for the logical Session transition. Persistence records that transition; it does not replace it.

## Atomic pending-result creation

When `commit_reconciliation(...)` receives a reconciliation whose physical outcome carries a `ResultEnvelope`, SQLite stores all three of these in the same transaction:

- the reconciliation record;
- the successor durable capacity head;
- the full `PendingLogicalResult` including the original `ResultEnvelope`.

A transport failure without a `ResultEnvelope` creates no pending logical result.

This removes the interval in which capacity could be canonically released while the logical result existed only in coordinator memory.

## Pending result identity

`PendingLogicalResult` binds:

- runner ID and capability digest;
- logical Session ID and attempt;
- ExecutionSpec ID and digest;
- physical authorization ID;
- reconciliation ID and digest;
- the complete `ResultEnvelope`.

Loading a pending result verifies its own metadata and then verifies that the exact reconciliation still exists and matches the same runner, Session, spec, authorization, and result digest.

## Logical submission

`prepare_logical_result_submission(...)` requires the exact running Session and reruns the existing `submit_result(session, result)` transition.

The resulting `LogicalResultSubmission` records:

- the exact pending result;
- the source running Session digest;
- the exact `result_submitted` Session returned by `submit_result`.

`commit_result_submission(...)` persists the submission append-only. Exact replay after a lost acknowledgement is idempotent; a different submission for the same logical Session attempt is a conflict.

## Restart recovery

After reconciliation but before submission, a restart can reload the pending full `ResultEnvelope`.

After submission, a later restart can reload the exact `result_submitted` Session and result digest. Therefore neither side of the logical handoff depends on transient coordinator memory.

## SQLite store schema v3

The reference store adds:

- `ge_pending_results`;
- `ge_result_submissions`.

Schema v1 can migrate directly. Schema v2 can migrate only when its historical reconciliations do not contain a completed physical result whose original `ResultEnvelope` is unavailable.

If a v2 reconciliation has `result_digest != None` but the full historical result body is absent, migration fails closed rather than reconstructing evidence from a digest.

Failure-only v2 reconciliations can migrate safely.

## Conformance bank

The repository includes 16 targeted tests covering atomic pending creation, failure-without-pending behavior, restart recovery, exact Session submission, wrong-Session rejection, durable submission recovery, lost-ack replay, missing-pending rejection, metadata consistency, logical failed-result preservation, orphan-pending rejection, fail-closed completed v2 migration, and safe failure-only v2 migration.

These tests are part of the candidate bank; the stacked v0.0.5+ line still awaits the full historical repository regression in a complete runner environment before promotion to canonical `main`.

## Boundary

The handoff persists an already-admitted `ResultEnvelope` and the existing logical Session transition. It does not decide whether the result is domain-correct, verified, integrated, approved, or releasable.

## Next boundary

The next high-value milestone is a durable logical Session registry covering the full lifecycle (`bound -> running -> revoked/result_submitted`) so restart recovery no longer depends on clients reconstructing the pre-result Session state.
