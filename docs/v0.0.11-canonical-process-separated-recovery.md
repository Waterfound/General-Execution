# v0.0.11 — Process-Separated Canonical Cold Recovery

General Execution v0.0.11 strengthens the v0.0.10 cold-recovery evidence boundary by running preparation and recovery in different Python interpreter processes.

## Boundary

The process harness executes:

```text
parent harness
  -> child A: prepare
     -> persist coordinator context
     -> persist PREPARED dispatch intent
     -> commit canonical capacity
     -> persist SUBMISSION_UNKNOWN
     -> exit

parent harness
  -> child B: resume
     -> receive only capacity/context/dispatch SQLite paths
     -> reconstruct durable context
     -> recover capacity and dispatch state
     -> report reconcile_provider
     -> exit
```

No `ExecutionSpec`, registry, plan, Session, authorization, lease, dispatch intent, or other Python protocol object is passed from child A to child B.

## Process evidence

Each worker emits an execution-only envelope containing:

- phase;
- PID and parent PID;
- a fresh process token;
- bounded protocol payload;
- payload digest.

`CanonicalProcessSeparatedEvidence` requires:

- prepare and resume use different PIDs;
- prepare and resume use different process tokens;
- neither worker is the parent harness process;
- both workers are direct children of the harness;
- recovered action remains `reconcile_provider`.

Process identity is evidence, not canonical protocol state. The run-specific `evidence_digest` therefore differs between executions, while `semantic_digest` binds only the deterministic protocol result.

## Durable bridge

The only intended state bridge between the two interpreters is the three SQLite stores:

```text
capacity.db
context.db
dispatch.db
```

The resume worker accepts only these paths. It calls the v0.0.10 strict cold bootstrap and cannot receive retained preparation objects as arguments.

## Authority boundary

Process separation does not widen execution authority:

```text
context_mode = cold_reconstructed
recovery_action = reconcile_provider
blind_resubmissions_authorized = 0
provider_outcomes_inferred = 0
```

The existing v0.0.7-v0.0.9 reconciliation/conformance gates remain responsible for resolving provider ambiguity.

## Focused conformance bank

The v0.0.11 bank covers five process-level cases:

1. prepare and resume execute as distinct direct child processes;
2. cold recovery preserves `reconcile_provider` and zero authority widening;
3. resume reconstructs the same context and invocation identity;
4. fresh directories reproduce the same semantic digest while process evidence differs;
5. replaying the same durable stores from new processes is semantically exact.

## Targeted evidence


The local workspace is a reconstructed offline harness over the canonical v0.0.10 logic. The result is targeted process-boundary evidence, not the complete historical repository regression.

## Next ceiling

With durable context, crash ordering, lost-ack replay, and process-separated reconstruction now covered, additional provider-neutral restart abstractions are expected to have diminishing returns.

The next material gates are:

1. complete historical repository regression on the canonical stacked line;
2. provider-specific execution of the v0.0.9 conformance harness with trustworthy run provenance;
3. only after those gates, consideration of concrete remote transport.
