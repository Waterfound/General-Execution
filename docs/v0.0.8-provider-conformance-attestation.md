# v0.0.8 — Provider Reconciliation Conformance & Attestation

General Execution v0.0.8 separates a provider's declared reconciliation contract from independently recorded evidence that the exact adapter revision satisfies that contract.

## Why v0.0.8 exists

v0.0.7 can make a conservative reconciliation decision from provider evidence. However, a provider or adapter declaration such as `same_operation` is not itself proof that repeated use of one `invocation_id` is actually idempotent.

v0.0.8 inserts a second gate before same-invocation resubmission can become transport-eligible:

```text
ReconciliationDecision
  + ProviderConformanceEvidence
  + exact adapter revision
  -> ProviderContractAttestation
  + fresh LiveDispatchPermit
  -> AttestedResubmissionPermit
```

No concrete remote transport is introduced by this version.

## Conformance evidence

`ProviderConformanceEvidence` binds:

- exact provider reconciliation contract digest;
- immutable adapter revision (40- or 64-hex);
- conformance suite version;
- environment scope;
- unique case results and their evidence digests.

Supported environment scopes are:

- `sandbox` — useful evidence, but insufficient to certify safe production resubmission;
- `production_equivalent` — eligible for certification when every required case passes.

`production_equivalent` is a property of the supplied conformance evidence. v0.0.8 does not pretend that naming evidence production-equivalent proves the underlying run occurred. The next executable harness boundary must produce and bind these artifacts rather than relying on manual declarations.

## Required cases

Every reconciliation-capable contract must provide:

1. `same_request_semantics` — same invocation ID + same request behaves exactly as declared;
2. `different_request_rejection` — same invocation ID + different request is rejected;
3. `lookup_identity_binding` — lookup is bound to invocation and request identity;
4. `absence_semantics` — `ABSENT` has stable semantics and does not hide accepted work.

If the contract claims terminal evidence lookup, it must additionally provide:

5. `terminal_evidence_binding` — terminal evidence is retrievable and bound back to the same invocation.

Missing required cases fail closed. Failed cases may produce an attestation artifact, but that attestation is non-conformant and cannot certify safe resubmission.

## Attestation

`ProviderContractAttestation` is deterministically derived from the exact contract and conformance evidence.

It binds:

- contract digest;
- immutable adapter revision;
- conformance evidence digest;
- environment scope;
- passed and failed required cases;
- contract-conformant status;
- safe-resubmission certification;
- terminal-evidence certification.

The attestation itself has:

```text
authority = NONE
```

It describes evidence. It does not submit work.

`safe_resubmission_certified` can only be true when:

- all required cases pass;
- environment scope is `production_equivalent`;
- the provider contract itself has strong idempotent resubmission semantics.

Sandbox evidence may prove logical conformance but can never set `safe_resubmission_certified=true`.

## Two independent evidence lineages

v0.0.8 deliberately keeps two evidence chains separate.

### Reconciliation evidence

Answers:

> What does the provider say happened to this exact invocation now?

It is already bound into `ReconciliationDecision.evidence_digest`.

### Conformance evidence

Answers:

> What evidence supports trusting this exact adapter revision's reconciliation/idempotency contract?

It is bound into `ProviderContractAttestation.conformance_evidence_digest`.

The final permit preserves both digests independently. Conformance evidence must never replace invocation-specific reconciliation evidence, and reconciliation evidence must never be mistaken for proof that the adapter's general idempotency semantics are correct.

## Attested resubmission permit

`AttestedResubmissionPermit` is the first artifact in this chain that carries narrow resubmission authority:

```text
authority = IDEMPOTENT_RESUBMIT_ONLY
new_physical_attempt_authorized = false
```

It binds:

- reconciliation decision digest;
- invocation-specific reconciliation evidence digest;
- provider contract digest;
- provider contract attestation digest;
- conformance evidence digest;
- fresh live dispatch permit digest;
- immutable adapter revision;
- exact invocation ID and request digest.

Issuance requires all of the following at the same gate:

1. the v0.0.7 decision is `resubmit_same_invocation`;
2. the decision still authorizes resubmission;
3. the decision's invocation and request match the durable dispatch intent;
4. the exact contract has a verified production-equivalent safe-resubmission attestation;
5. the exact adapter revision matches the attested revision;
6. the `LiveDispatchPermit` still verifies against the current canonical durable capacity head.

A Session revocation or capacity-state change can therefore invalidate an otherwise valid conformance attestation path because the live execution authority is checked again at issuance.

## Same invocation, never a new retry

The attested permit cannot authorize `physical_attempt + 1`.

It authorizes only an idempotent repeat of the exact already-ambiguous invocation. A new physical attempt remains governed by the native retry path and requires a terminal admitted non-completed outcome.

## Remaining distributed race

Even an attested permit cannot make a local transaction atomic with an arbitrary remote provider side effect. A future transport adapter must reverify the live/attested permit immediately before issuing the provider request and must rely on the provider's proven invocation-level idempotency.

This is why concrete remote transport remains disabled in v0.0.8.

## v0.0.8 conformance target

The focused candidate bank covers:

- production-equivalent all-pass certification;
- sandbox non-certification;
- missing required cases;
- duplicate case IDs;
- failed mandatory case handling;
- unsafe `may_duplicate` contract handling;
- conditional terminal-evidence case requirement;
- wrong contract digest;
- wrong adapter revision;
- tampered attestation;
- sandbox attestation rejection at resubmission gate;
- production attestation issuing same-invocation-only permit;
- stale live permit after Session revocation;
- permit tampering;
- explicit separation of reconciliation and conformance evidence lineages;
- attestation case-identity hardening.

## Next ceiling

The next highest-value boundary is an **executable provider conformance harness**.

Rather than accepting manually assembled case results, the harness should exercise a provider/adapter implementation and generate the case evidence itself. A reference provider can prove the harness semantics locally first. Provider-specific adapters can later run the same suite against their sandbox or production-equivalent environment.

Only after executable conformance evidence exists should General Execution consider a concrete remote transport adapter.

## Authority invariant

> Conformance may certify a narrow execution property. It does not create project authority.

General Execution still cannot decide what should be built, whether output evidence is sufficient for integration, or whether anything should be promoted or released.
