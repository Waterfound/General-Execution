# v0.0.7 — Post-Restart Provider Reconciliation

## Goal

Resolve a persisted `in_flight_unknown` lease after restart without guessing provider state, creating a duplicate canonical execution, or expanding General Execution's authority.

## Reconciliation boundary

Restart recovery from v0.0.5 preserves an active capacity lease as `RecoveredInFlightLease(status="in_flight_unknown")`. v0.0.7 adds the protocol that can turn that unknown occupancy into one explicit capacity release.

Only two resolution classes are admitted:

1. an already-verifiable `PhysicalOutcomeBundle` for the exact physical authorization;
2. an explicitly revoked logical `ExecutionSession` that owns the exact lease.

Absence of provider response, local restart, coordinator timeout, or elapsed wall-clock time is not a resolution.

## Plan before commit

Reconciliation is split into a deterministic plan and a persistence commit.

A `RecoveryReconciliationPlan` binds:

- the complete source durable snapshot;
- the exact recovered lease;
- the resolution kind;
- the provider-outcome or revoked-session evidence digest;
- the exact capacity-release digest;
- the complete target durable snapshot.

The target must be a direct durable successor of the source and may add exactly one capacity-release transition. The source snapshot is embedded in the plan so an idempotent replay can still prove the complete historical source -> release -> target relationship.

## Provider-outcome path

`plan_provider_outcome_reconciliation(...)` reuses the existing physical-outcome and capacity-release verification from v0.0.3/v0.0.4. The outcome must reproduce against the original `ExecutionSpec`, registry, dispatch plan, Session, runner, and physical authorization represented by the recovered lease.

A completed physical outcome releases capacity, but v0.0.7 does not automatically call `submit_result`. Logical result submission remains a separate explicit protocol step.

## Revocation path

`plan_revocation_reconciliation(...)` accepts only a Session already in the `revoked` state and only when that Session exactly owns the recovered capacity lease.

Revocation releases occupancy; it does not manufacture a provider failure or result.

## Atomic commit

`commit_reconciliation(...)` compares the SQLite canonical head with the plan.

- If the source snapshot is still canonical, the target is committed through the v0.0.6 atomic CAS adapter.
- If the exact target is already canonical, replay is idempotent and returns a receipt without creating another transition.
- Any other canonical head causes a reconciliation conflict.

This means two different resolutions planned from the same recovered head cannot both become canonical. For example, provider outcome and Session revocation may race, but the first committed successor wins and the other becomes stale.

## Lost acknowledgement

Because the plan contains both complete source and target snapshots, the same plan can be replayed after an acknowledgement loss. If its exact target is already canonical, General Execution returns an idempotent reconciliation receipt while still re-verifying the source-to-target relationship.

## Authority boundary

Reconciliation resolves durable capacity occupancy only. It does not decide whether application-domain evidence is correct, whether a result should be accepted by Build Colony or another client, whether integration should happen, or whether anything should be released to users or consensus.

## Conformance bank

The v0.0.7 tests cover exact provider-outcome reconciliation, atomic durable-head advancement, idempotent lost-ack replay, explicit revocation, rejection of unrevoked Sessions, recovered-lease mismatch, foreign physical outcomes, competing outcome/revocation plans, stale-plan rejection, completed-outcome occupancy release without automatic Session submission, receipt consistency, and release-digest consistency.

## Next boundary

After the stacked v0.0.5-v0.0.7 line is admitted, the next high-value boundary is **provider reattachment semantics**: define how a concrete provider reports the status of a previously dispatched `provider_invocation_id` after restart, while keeping provider polling separate from execution authority.
