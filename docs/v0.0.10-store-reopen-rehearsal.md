# v0.0.10 — Durable Store Reopen Rehearsal

## Goal

Join the v0.0.5-v0.0.9 persistence/recovery stack in one deterministic QA scenario that closes and reopens the durable capacity store and provider registry while keeping the immutable execution context explicitly caller-retained.

v0.0.10 does **not** claim a cold coordinator restart. That requires durable reconstruction of the `ExecutionSpec`, registry, dispatch plan, logical Session, and physical authorization and is the next protocol boundary.

## Context mode

Every `StoreReopenRehearsalReport` is fixed to:

```text
context_mode = caller_retained
```

This makes the evidence boundary explicit. The rehearsal proves durable store/recovery mechanics while the caller retains the exact execution context needed by v0.0.8 physical-outcome admission.

## Rehearsal sequence

`run_reference_store_reopen_rehearsal(...)` performs:

```text
caller-retained ExecutionSpec / plan / Session / authorization
  -> capacity lease
  -> durable capacity snapshot persisted by v0.0.6
  -> deterministic provider registration persisted by v0.0.9
  -> both SQLite stores closed/reopened
  -> v0.0.5 recovered in_flight_unknown lease
  -> v0.0.8 provider status probe
  -> running status admitted as keep_running
  -> provider terminal observation persisted
  -> terminal status admitted as PhysicalOutcomeBundle
  -> v0.0.7 reconciliation plan
  -> v0.0.6 atomic durable-head commit
```

The capacity store and provider registry are required to be distinct filesystem-backed SQLite files.

## Preflight

Before the first protocol commit, the rehearsal checks that the capacity store has no canonical head for the reference runner and that the deterministic provider key is absent from the provider registry.

The two stores cannot be made transactionally atomic with one another by the core protocol. A failure between capacity-head commit and provider registration therefore remains a legitimate future cut point; the resulting state is conservative because the capacity lease remains durable and cannot be silently reused.

## Running checkpoint

After reopening both stores, the provider `running` observation is passed through v0.0.8 `assess_provider_status(...)`. The only accepted disposition is `keep_running` with no physical outcome. Capacity remains occupied.

## Terminal scenarios

### `timed_out`

The reference provider records a terminal transport timeout. v0.0.8 admits the physical observation, v0.0.7 releases capacity, and the logical Session remains `running`. No logical result exists.

### `completed`

The reference provider records a completed `ResultEnvelope`. Physical admission and capacity reconciliation complete, but the logical Session still remains `running`.

The caller may later invoke `submit_result(session, result)` as a separate explicit step. The rehearsal never performs it automatically.

```text
physical completion != logical result submission
```

## Deterministic report

`StoreReopenRehearsalReport` binds the provider identity, durable heads, recovered lease, running status/assessment, terminal status, physical outcome, reconciliation plan/receipt, committed capacity head, Session state, optional result digest, and the explicit `caller_retained` context mode.

`ReferenceStoreReopenRehearsal` rechecks the report against its recovered lease, physical outcome, result, and reconciliation receipt so a substituted component is rejected.

Fresh stores with the same suffix and terminal mode reproduce the same protocol report independent of filesystem path.

## Authority boundary

v0.0.10 is a QA facility only. It does not execute arbitrary commands or user workloads and does not gain domain verification, integration, release, or consensus authority.

## Conformance bank

Tests cover timeout reconciliation, completed physical outcome without automatic logical submission, terminal provider persistence, deterministic fresh-store replay, capacity-head reuse rejection, distinct-store enforcement, invalid-mode rejection before store mutation, report/component binding, and explicit `caller_retained` context semantics.

## Admission boundary

v0.0.10 remains stacked above the v0.0.5-v0.0.9 candidates. It is not evidence that the full historical repository regression has passed. Canonical `main` remains unchanged.

## Next boundary

The next highest-value milestone is **v0.0.11 — Durable Recovery Context**: canonically serialize and reconstruct the immutable execution context required after a true coordinator process restart, then rerun this rehearsal with all volatile protocol objects discarded.
