# v0.0.12 — Process Crash Cut-Point Matrix

General Execution v0.0.12 takes the v0.0.10 crash-ordering semantics and v0.0.11 process separation one step further: the preparation worker terminates abruptly with `os._exit(91)` immediately after a selected durable cut point, and a fresh interpreter then performs strict cold recovery.

## Cut points

The canonical matrix is:

```text
context_only
  -> prepared
  -> capacity_committed
  -> submission_unknown
```

The required recovery dispositions are:

```text
context_only        -> inert_orphan
prepared            -> inert_orphan
capacity_committed  -> begin_submission
submission_unknown  -> reconcile_provider
```

## Why abrupt termination matters

The cut worker emits bounded process evidence and then calls `os._exit(91)`. This bypasses normal Python exception unwinding and interpreter shutdown hooks after the selected durable operation has returned.

The recovery worker is a distinct direct child process. It receives only the three SQLite store paths and reconstructs state through the canonical v0.0.10 strict bootstrap.

## Safety properties

The matrix confirms the intended persistence ordering:

- context persistence alone cannot create canonical occupancy;
- a durable `PREPARED` intent still cannot create canonical occupancy;
- after capacity CAS, context and dispatch identity already exist and recovery may only continue with `begin_submission`;
- after `SUBMISSION_UNKNOWN`, recovery preserves ambiguity and returns `reconcile_provider`;
- no cut point silently releases capacity;
- no cut point invents a provider outcome;
- no cut point authorizes blind resubmission.

The process-specific PID/token envelope is evidence only; semantic identity remains bound to context, invocation, cut point, and recovery disposition.

## Focused conformance bank

The v0.0.12 bank covers five cases:

1. abrupt exit after context persistence -> inert orphan;
2. abrupt exit after PREPARED persistence -> inert orphan;
3. abrupt exit after capacity commit -> `begin_submission`;
4. abrupt exit after `SUBMISSION_UNKNOWN` -> `reconcile_provider`;
5. the complete ordered matrix runs with distinct cut/recovery processes and unique semantic cut-point digests.

## Local ceiling

At v0.0.12, provider-neutral restart/recovery has evidence for:

- durable context reconstruction;
- safe write ordering;
- lost-ack replay;
- separate interpreter recovery;
- abrupt process termination at every pre-provider canonical cut point.

Further provider-neutral restart abstractions are now expected to have diminishing returns.

The next material gates are external/evidence-oriented:

1. complete historical repository regression on a full checkout;
2. provider-specific execution of the v0.0.9 conformance harness with trustworthy run provenance;
3. only after those gates, consideration of concrete remote transport.
