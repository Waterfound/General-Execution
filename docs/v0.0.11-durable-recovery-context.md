# v0.0.11 — Durable Recovery Context

## Goal

Make the execution identity required for post-restart reconciliation reconstructable from durable state instead of relying on caller-retained Python objects, then prove that reconstruction through a true cold coordinator rehearsal.

v0.0.10 deliberately proved only a store-reopen boundary with execution context retained by the caller. v0.0.11 closes that missing context layer.

## Durable context

`DurableRecoveryContext` persists the exact execution objects needed to re-enter the existing protocols:

- `ExecutionSpec`;
- `RunnerRegistry` and selected runner identity;
- deterministic `DispatchPlan`;
- running logical `ExecutionSession`;
- `PhysicalAttemptAuthorization` including retry predecessor bindings;
- an anchor `DurableCapacitySnapshot` containing the exact active lease;
- recovered lease identity and digest.

The serialized form is canonical JSON with strict nested schema checks. Loading reconstructs typed objects and re-runs the existing plan, dispatch-request, capacity-state, authorization, and lease bindings.

## Anchor semantics

The context is anchored to the capacity snapshot at which the physical attempt became recoverable, but it does not require the current durable head to remain frozen forever.

A current capacity snapshot may contain later independent transitions while the same lease remains active. The context remains valid only when:

1. both anchor and current capacity snapshots replay for the recovered runner;
2. the current transition history contains the complete anchor transition prefix;
3. the exact recovered lease remains active and unchanged;
4. the persisted spec / registry / plan / Session / authorization still reproduce the same physical attempt.

This allows `max_parallelism > 1` without invalidating a long-running lease merely because another slot advanced the runner head.

## Immutable context store

`SQLiteRecoveryContextStore` is filesystem-backed and immutable per physical authorization.

The first exact context is stored. Exact replay is idempotent. A later attempt to associate the same authorization with a different context is rejected rather than silently re-anchored.

The store uses WAL and `synchronous=FULL`. `:memory:` is intentionally rejected.

## Cold bootstrap

`bootstrap_active_recovery_contexts(...)` begins from only the recovery-context store and the durable capacity-head store.

The context store is self-contained enough to reconstruct runner capabilities from its anchor context. The capacity store can then be opened with that runner definition and the current canonical capacity head can be replayed.

The bootstrap returns an active binding only when the context still corresponds to an exact active recovered lease.

Two non-active states are intentionally harmless:

- **orphan context:** context became durable but the capacity head was never committed; bootstrap ignores it;
- **historical context:** the lease was later canonically released; bootstrap ignores it.

## Safe persistence order

The intended ordering for a recoverable physical attempt is:

```text
reserve candidate in memory
  -> build anchor snapshot + recovery context
  -> persist recovery context
  -> commit durable capacity head
  -> register provider identity / begin provider-side lifecycle
```

This ordering is fail-safe:

- crash after context persistence but before capacity commit leaves only an orphan context;
- once an active capacity head is committed, its recovery context already exists;
- provider registration happens only after both coordinator-side recovery records are durable.

## True cold coordinator rehearsal

The v0.0.11 reference rehearsal is intentionally split into two APIs.

`prepare_reference_cold_restart(...)` creates the physical attempt and persists three distinct filesystem-backed stores:

1. recovery context;
2. canonical capacity head;
3. provider registry identity/status.

`resume_reference_cold_restart(...)` receives only those three paths. It receives no live `ExecutionSpec`, `RunnerRegistry`, `DispatchPlan`, `ExecutionSession`, runner object, or `PhysicalAttemptAuthorization` from the preparation phase.

Resume performs:

```text
recovery-context store + capacity store
  -> cold bootstrap
  -> reconstructed runner / Spec / registry / plan / Session / authorization
  -> recovered in_flight_unknown lease
  -> provider status probe
  -> running => keep_running, no outcome, capacity still occupied
  -> terminal provider observation
  -> physical outcome admission
  -> v0.0.7 reconciliation
  -> canonical capacity release
```

The report marks this boundary explicitly as `context_mode="cold_reconstructed"`.

A completed physical outcome still leaves the reconstructed logical Session `running`; `submit_result(...)` remains a separate explicit operation.

Therefore the existing boundary remains:

```text
physical completion != logical result submission
```

## Authority boundary

Recovery context preserves identity. Cold bootstrap and rehearsal do not create permission to retry, release capacity without terminal/revocation evidence, submit a logical result automatically, validate application evidence, integrate changes, or approve release.

`Execution consumes authority. It does not create authority.` remains unchanged.

## Conformance bank

The v0.0.11 repository bank covers canonical context round-trip, reconstruction of exact execution objects, validity across unrelated capacity-head advancement, rejection after lease removal, strict nested schema handling, Session-binding changes, filesystem persistence/reopen, idempotent replay, re-anchor conflict, bootstrap reconstruction without live coordinator objects, metadata/schema corruption, filesystem-only storage, unknown authorization lookup, orphan-context bootstrap, historical released-context bootstrap, true stores-only cold resume, completed cold recovery without automatic logical submission, provider identity reconstruction, deterministic cold replay across fresh files, context-metadata corruption, distinct-store enforcement, invalid resume mode preservation, and final report binding.

## Admission boundary

v0.0.11 remains stacked above the v0.0.5-v0.0.10 candidate line. Targeted protocol evidence does not substitute for the full historical repository regression. Canonical `main` remains unchanged until that larger gate is executed.

## Next boundary

The next highest-value milestone is a **cross-store cut-point failure matrix**. It should inject interruption at the boundaries around context persistence, capacity-head commit, provider registration, terminal-state persistence, and reconciliation CAS, then prove the exact recoverable state at every cut point without timing assumptions.
