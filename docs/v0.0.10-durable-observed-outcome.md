# v0.0.10 — Durable Observed Outcome

## Goal

Close the restart gap between a durable dispatch becoming `observed` and the canonical capacity lease being released.

Before this milestone, `SqliteDispatchIntentStore.record_observed()` verified the complete `PhysicalOutcomeBundle` but persisted only outcome/observation/receipt digests and transport metadata in `DispatchIntentState`. After a coordinator crash, those hashes proved which outcome had been admitted but were not sufficient to reconstruct the exact object required by `release_capacity_for_outcome()`.

v0.0.10 retains the complete admitted physical outcome bytes atomically with the `observed` dispatch transition.

## Canonical path

```text
submission_unknown dispatch
        +
verified PhysicalOutcomeBundle
        |
        v
BEGIN IMMEDIATE
        |
        +-- dispatch state -> observed
        |
        +-- canonical full outcome bytes
        |
        v
COMMIT
        |
        v
restart-safe exact outcome reload
        |
        v
normal release_capacity_for_outcome()
        |
        v
durable capacity CAS
```

The outcome store does not invent a new release rule. After restart it reconstructs the exact `PhysicalOutcomeBundle`, reruns the normal execution-context verifier, and then calls the existing capacity-release protocol.

## Canonical codec

`physical_wire.py` provides a canonical JSON codec for:

- `PhysicalAttemptAuthorization` including the exact `AdapterDispatchRequest` and retry predecessor bindings;
- `PhysicalObservation` including the complete `ResultEnvelope` when transport completed;
- `PhysicalReceipt`;
- `PhysicalOutcomeBundle`.

Deserialization is fail-closed. The reconstructed bundle must pass the existing intrinsic physical-outcome verification, including authorization/request identity, observation response digest, receipt bindings, terminal status semantics, result identity, and retry lineage fields.

A completed outcome therefore retains the complete logical result bytes, not only its digest.

## Durable observed-outcome record

`DurableObservedOutcome` binds the exact:

- dispatch intent and observed-state digest;
- runner;
- lease ID and lease digest;
- authorization ID and authorization digest;
- invocation ID and request digest;
- physical-attempt ordinal;
- outcome, observation, and receipt digests;
- transport status;
- complete physical outcome payload.

Metadata and payload must reproduce one another during every load.

## Atomicity

`SqliteDurableObservedOutcomeStore` extends the existing durable dispatch outbox.

Its `record_observed()` performs the dispatch-state update and full-outcome insert under the same SQLite `BEGIN IMMEDIATE` transaction. Before commit it rereads both rows and verifies that they reproduce the candidate exactly.

Consequences:

- a crash cannot leave a canonical v0.0.10 `observed` transition without its outcome bytes;
- a crash cannot expose outcome bytes while the dispatch state is still `submission_unknown`;
- one intent/authorization/invocation cannot silently acquire two different canonical outcomes;
- exact replay after a lost acknowledgement is idempotent;
- a conflicting replay fails closed.

The older `SqliteDispatchIntentStore` remains as a compatibility surface for the earlier protocol. It does not by itself satisfy the v0.0.10 restart-complete outcome-durability invariant.

## Restart release recovery

`release_observed_capacity_after_restart()` performs only a bounded mechanical recovery:

1. load the exact durable `observed` dispatch state;
2. load and verify the complete durable outcome;
3. rerun `verify_physical_outcome()` against the supplied spec/registry/plan/Session/runner;
4. load the canonical durable capacity state;
5. require the exact active lease identified by lease/auth/invocation/physical-attempt bindings;
6. call the existing `release_capacity_for_outcome()`;
7. commit the resulting capacity state through `SqliteCapacityHeadStore` compare-and-swap.

If the exact outcome release is already canonical, recovery returns an idempotent result instead of attempting a second release.

If the outcome is neither backed by the exact active lease nor by the exact already-canonical release, recovery fails closed.

## Relationship to provider reconciliation

This milestone is complementary to v0.0.7–v0.0.9 provider reconciliation and conformance.

Those layers answer whether a provider operation exists, whether same-invocation resubmission is safe, and whether provider behavior matches an attested contract. v0.0.10 begins only after a physical outcome has been admitted. It ensures that the admitted outcome remains available after restart so the already-defined local capacity transition can finish deterministically.

No provider-reconciliation semantics are weakened or bypassed.

## Conformance bank

The candidate branch contains 14 focused tests covering:

- failure-outcome canonical round trip;
- completed-outcome round trip with the complete `ResultEnvelope`;
- nested result tamper rejection;
- observed-state plus full-outcome persistence across reopen;
- exact lost-ack replay;
- conflicting second outcome rejection;
- missing outcome bytes fail-closed behavior;
- metadata tamper detection;
- outcome-payload tamper detection;
- observed-outcome runner recovery;
- restart-driven capacity release;
- idempotent release replay;
- wrong execution-context rejection;
- completed-outcome release after restart.

The bank is committed as candidate evidence. No 14/14 execution claim is made until the full branch can be materialized in a runnable environment without consuming the user's GitHub Actions quota.

## Authority boundary

Durable outcome storage is execution mechanics. It does not decide whether the workload should exist, whether engineering evidence is correct, whether a result should be integrated, or whether anything should be released to users.

> Execution consumes authority. It does not create authority.

## Next boundary

After v0.0.10 receives executable regression evidence, the next convergence step is to connect this restart-complete physical-outcome path to a durable logical Session/result lifecycle without importing the parallel prototype wholesale. Any such addition should be adapted to the canonical dispatch/provider architecture now present in `main`.
