# v0.0.12 — Bounded Recovery Driver

## Goal

Turn the deterministic v0.0.11 Session recovery projection into a narrowly bounded executor for restart catch-up.

The driver consumes one exact `SessionRecoveryProjection`, recomputes it from the durable stores immediately before acting, and applies at most one named mechanical action.

It does **not** become a scheduler, retry policy, provider transport, provider-reconciliation agent, verifier, integrator, or release authority.

> **Recovery applies already-determined mechanical state transitions. It does not create new execution authority.**

## Entry point

```python
apply_recovery_step(
    spec,
    registry,
    plan,
    runner,
    capacity_store,
    dispatch_store,
    projection,
)
```

The supplied projection is accepted only if `project_session_after_restart()` reproduces it exactly against the current canonical durable state.

A stale projection fails closed.

## Action matrix

| Projection action | Driver behavior | Transport authority | Automatic retry |
| --- | --- | --- | --- |
| `none` | return `no_action` | no | no |
| `start_session` | deterministically reproduce `bound -> running` in memory | no | no |
| `prepare_dispatch_intent` | reconstruct the exact physical authorization and persist the deterministic intent | no | no |
| `begin_submission` | advance the durable outbox to `submission_unknown` and return the non-transport `DispatchPermit` digest | no | no |
| `reconcile_provider` | return `external_input_required` without mutating provider state | no | no |
| `release_observed_capacity` | re-admit the durable full outcome and finish canonical capacity release | no | no |

`legacy_untracked` and `inconsistent` projections are refused.

## Retry reconstruction

An active retry lease can require reconstruction of physical authorization after coordinator restart.

For physical attempt `N > 1`, the driver locates exactly one durable predecessor outcome satisfying all of:

- same logical Session identity;
- same logical attempt;
- predecessor physical attempt `N - 1`;
- exact `previous_invocation_id`;
- exact `previous_receipt_digest`.

It then calls the ordinary `authorize_retry()` path with the lease's existing invocation ID and requires the reconstructed authorization ID and digest to match the capacity lease exactly.

The driver never creates a new retry lease and never interprets `retry_eligible=true` as permission to retry.

## Stale and concurrent state

The first gate is full projection equality. If any relevant durable state changed since the caller obtained the projection, the driver raises `RecoveryDriverError("recovery projection is stale")`.

The underlying stores retain their existing CAS and active-capacity checks, so a race after the projection check still cannot grant transport authority.

A relevant example is concurrent Session revocation while `prepare_dispatch_intent` is being recovered:

1. the driver may have already reproduced the deterministic intent from the previously active lease;
2. another coordinator canonically releases that lease for Session revocation;
3. a prepared intent may remain as durable evidence;
4. the post-action Session projection becomes `revoked`;
5. `begin_submission()` refuses the prepared intent because the canonical capacity lease is no longer active;
6. the driver reports the post-action `revoked` Session and still grants no transport authority.

Thus a losing recovery action can leave conservative durable evidence, but cannot resurrect execution authority.

## Result object

`RecoveryDriverResult` binds:

- source projection digest;
- named action;
- status (`applied`, `no_action`, or `external_input_required`);
- resulting Session and digest;
- optional dispatch-state digest;
- optional dispatch-permit digest;
- optional capacity-recovery digest;
- optional next-projection digest;
- `transport_authority=False`;
- `automatic_retry_authorized=False`.

For durable mutations, the resulting Session is taken from the freshly recomputed post-action projection. This prevents race reporting from returning a stale logical Session after another coordinator has already established a terminal state.

## Provider reconciliation boundary

`reconcile_provider` is deliberately not executed by this driver.

Provider reconciliation can depend on external evidence, provider-specific semantics, conformance attestation, and a fresh live dispatch permit. The driver therefore returns `external_input_required` and leaves the durable state unchanged.

Likewise, the `DispatchPermit` returned after `begin_submission` still has `transport_authority=False`. Real transport continues to require the separate live-dispatch/provider-conformance gates.

## Conformance bank

The branch contains 12 focused v0.0.12 tests covering:

- bounded `start_session` recovery;
- first-attempt dispatch-intent recovery;
- physical retry authorization reconstructed from exact durable predecessor outcome;
- `begin_submission` without transport authority;
- provider reconciliation requiring external input;
- failed observed outcome -> canonical capacity release without automatic retry;
- completed observed outcome -> deterministic `result_submitted` projection;
- coherent `retry_eligible` state producing `no_action`;
- coherent revoked state producing `no_action`;
- refusal of legacy incomplete evidence;
- stale projection rejection after another coordinator advances dispatch;
- concurrent revocation winning over dispatch preparation without restoring transport authority.

The bank is committed as development evidence but is not described as an executed 12/12 result until the complete candidate tree is materialized in a runnable environment.

## Boundary

v0.0.12 is still an execution-recovery mechanism only.

It cannot decide:

- whether retry is desirable;
- whether provider evidence is trustworthy;
- whether an execution result is correct;
- whether engineering evidence is sufficient;
- whether a result should be integrated;
- whether anything should be released.

Those authorities remain outside General Execution.

## Next boundary

After executable regression, the next useful question is not another recovery primitive. The higher-value gate is whether the complete local protocol can be exercised end-to-end through a concrete provider-specific sandbox while preserving the same recovery, idempotency, and authority boundaries.
