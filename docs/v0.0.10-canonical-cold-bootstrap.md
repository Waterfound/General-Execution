# v0.0.10 — Canonical Cold Coordinator Bootstrap

General Execution v0.0.10 converges cold-recovery work onto the canonical v0.0.5-v0.0.9 provider-neutral line. It does not replace the existing durable-capacity, dispatch, reconciliation, attestation, or conformance modules.

## Recovery context

`DurableCoordinatorContext` persists the exact execution identity required after coordinator-memory loss:

```text
ExecutionSpec
+ RunnerRegistry / selected runner
+ DispatchPlan
+ running ExecutionSession
+ PhysicalAttemptAuthorization
+ active CapacityLease identity
+ canonical DispatchIntent
```

The payload is canonical JSON with explicit typed codecs. The SQLite context store carries a durable store-schema marker and verifies row metadata against the reconstructed payload.

## Fail-safe persistence order

```text
coordinator context
  -> dispatch PREPARED
  -> canonical capacity reservation CAS
  -> dispatch SUBMISSION_UNKNOWN
```

This ordering provides four distinct crash states:

- **context only** — inert; no canonical capacity occupancy;
- **context + PREPARED** — inert; no canonical capacity occupancy;
- **capacity committed** — recover as `begin_submission`; context and dispatch identity already exist;
- **SUBMISSION_UNKNOWN** — recover as `reconcile_provider`; no blind retry and no inferred provider outcome.

An active lease without its matching durable dispatch intent is an integrity failure.

## Strict cold bootstrap

`bootstrap_cold_coordinator_strict()` reconstructs active bindings only from the three durable stores.

A capacity-head row is checked structurally before loading. Only true absence may be treated as a pre-commit orphan. If a row exists but fails snapshot replay, metadata verification, capability binding, or decoding, bootstrap fails closed.

Historical context whose lease is no longer active is ignored and cannot resurrect occupancy.

## Lost-ack replay

`prepare_canonical_cold_ambiguity()` is replay-safe through `SUBMISSION_UNKNOWN`.

Repeating an identical preparation after a lost acknowledgement:

- preserves the same physical invocation ID;
- does not repeat the capacity reservation CAS;
- does not advance the dispatch revision;
- reconstructs and verifies the same `DispatchPermit`;
- returns the same `CanonicalColdPreparationReceipt` and digest.

Replay fails closed after capacity has advanced beyond the original reservation or after provider observation has moved dispatch beyond `SUBMISSION_UNKNOWN`.

## Canonical cold rehearsal

`recover_canonical_cold_ambiguity()` accepts only capacity, context, and dispatch store paths. Its report freezes:

```text
context_mode = cold_reconstructed
recovery_action = reconcile_provider
blind_resubmissions_authorized = 0
provider_outcomes_inferred = 0
```

No concrete remote provider is introduced. Provider ambiguity is handed to the existing canonical reconciliation and conformance stack.

## Authority invariant

> Cold recovery restores execution identity and ambiguity. It does not create transport, retry, verification, integration, or release authority.

```text
restart != failure
restart != completion
SUBMISSION_UNKNOWN != retry
provider not_found != failure
```

## Focused conformance bank

The v0.0.10 bank contains twelve scenarios:

1. context-only orphaning;
2. PREPARED-before-capacity orphaning;
3. capacity-commit recovery as `begin_submission`;
4. `SUBMISSION_UNKNOWN` recovery only as `reconcile_provider`;
5. missing dispatch intent under an active lease fails closed;
6. corrupt capacity metadata fails closed;
7. context-store schema drift fails closed;
8. context-row metadata tampering fails closed;
9. full cold reconstruction preserves ambiguity;
10. lost-ack preparation replay is exact and non-mutating;
11. protocol artifacts are filesystem-path independent;
12. the three durable stores must be distinct files.

## Targeted evidence

An offline reconstructed harness executed the focused bank successfully:

```text
12 passed in 0.51 s
compileall: PASS
```

The harness used byte-identical Git blobs for the canonical base modules and for `context_codec.py`, `cold_guard.py`, and `canonical_cold.py`. `coordinator_context.py` and the local test driver were reconstructed with equivalent logic because the container cannot resolve GitHub hosts directly.

This is strong targeted evidence, but it is not represented as a byte-for-byte checkout run or the complete historical repository regression. No GitHub Actions were consumed.

## Next gate

The next local evidence boundary is process-separated canonical cold recovery: preparation and recovery in different Python interpreter processes, with the SQLite stores as the only bridge. Beyond that point, further confidence should primarily come from full historical regression and provider-specific trustworthy execution provenance.
