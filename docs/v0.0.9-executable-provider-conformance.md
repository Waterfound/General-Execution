# v0.0.9 — Executable Provider Conformance Harness

General Execution v0.0.9 turns the v0.0.8 conformance case model into an executable provider-neutral harness.

The harness exercises a target implementation and mechanically generates `ProviderConformanceEvidence` from observed submit/lookup/terminal behavior instead of requiring a caller to hand-assemble case results.

## Target contract

A `ProviderConformanceTarget` exposes:

- provider, adapter and adapter-version identity;
- immutable adapter revision;
- environment scope;
- reset/isolation operation;
- submit by `(invocation_id, request_digest)`;
- lookup by the same identity;
- terminal-evidence transition for the terminal lookup case.

The target identity must match the `ProviderReconciliationContract` before any case is run.

## Executed cases

`run_provider_conformance()` runs the following cases in isolated target state:

1. **same_request_semantics**
   - submit the same invocation and request twice;
   - verify the observed behavior matches `same_operation`, `duplicate_rejected`, or `may_duplicate` exactly.

2. **different_request_rejection**
   - submit one request;
   - reuse the same invocation ID with a different request digest;
   - require explicit rejection.

3. **lookup_identity_binding**
   - submit one invocation;
   - require lookup by the correct request to resolve the same provider operation;
   - require lookup with the same invocation but different request digest to report identity mismatch rather than silently matching or returning absence.

4. **absence_semantics**
   - require an unseen invocation to report absent;
   - submit it;
   - require the same lookup to stop reporting absent and resolve the accepted operation.

5. **terminal_evidence_binding** — only when claimed by the provider contract
   - submit one invocation;
   - transition it to terminal with a known terminal-evidence digest;
   - require lookup to return the same provider operation and exact terminal-evidence digest.

Each case result stores a digest of the harness version, case identity and observed transcript.

## Run artifact

`ProviderConformanceRun` binds:

- harness version;
- reconciliation-contract digest;
- provider / adapter / adapter version;
- immutable adapter revision;
- environment scope;
- exact case results;
- generated conformance-evidence digest;
- reconciled all-required-cases-pass flag.

The run is deterministic for deterministic target behavior and clean isolation.

## Reference target

v0.0.9 includes `ReferenceConformanceTarget`, an in-memory deterministic reference provider used to validate the harness itself.

It supports all three declared duplicate semantics:

- `same_operation`;
- `duplicate_rejected`;
- `may_duplicate`.

The reference target reports `sandbox`. Evidence generated from it can demonstrate harness semantics and may produce a logically conformant v0.0.8 attestation, but sandbox evidence cannot certify safe production resubmission.

The reference target is not a remote transport and does not make any provider-specific adapter production-ready.

## Detecting false declarations

The executable harness is designed to turn mismatches into failed cases rather than accepting declarations optimistically.

Examples covered by the candidate bank include:

- contract declares `same_operation`, target actually rejects the duplicate;
- lookup ignores request identity;
- accepted work is incorrectly reported as absent;
- terminal transition does not yield terminal evidence;
- target identity does not match the provider contract;
- malformed adapter revision or digest material.

A provider may legitimately conform to `may_duplicate`; that can yield a conformant case result while still remaining ineligible for safe automatic resubmission because the v0.0.8/v0.0.7 policy gates distinguish correctness of declaration from safety of semantics.

## Evidence provenance boundary

An important limitation remains intentionally explicit.

The harness can *produce* evidence from execution, but ordinary in-process Python objects are not cryptographic proof that an external execution actually happened. A malicious caller could still fabricate structurally valid evidence objects outside the harness.

No concrete remote transport consumes these artifacts in v0.0.9, so this is not currently a path to a provider side effect.

Before production-equivalent evidence can enable a real provider adapter, the system needs execution provenance that binds:

- the exact harness revision;
- exact provider adapter revision;
- target/environment identity;
- run artifact digest;
- conformance evidence digest;
- the mechanism that actually executed the suite.

That provenance may ultimately come from a trusted runner, signed build/attestation system, or another independently verifiable execution environment. The core should not pretend a self-asserted field proves that fact.

## v0.0.9 candidate bank

The focused harness tests cover:

- mechanically generated sandbox evidence;
- semantic determinism across clean runs;
- false same-request declaration detection;
- matching duplicate-rejected semantics;
- conformant-but-unsafe `may_duplicate` semantics;
- target identity mismatch;
- malformed adapter revision;
- lookup identity violation;
- absence-semantics violation;
- terminal-evidence violation;
- conditional terminal case omission;
- distinct request-digest requirement.

## Next ceiling

The next highest-value boundary is **trusted conformance-run provenance + provider-specific sandbox execution**.

Purely local modeling now has diminishing returns. The next evidence that materially changes confidence is to run this harness through a concrete adapter against an independently identifiable provider sandbox or equivalent target, while binding the produced run to trustworthy execution provenance.

Only after that evidence exists should concrete remote execution transport be considered.

## Authority invariant

> Executable conformance measures an execution property; it does not create project authority.

Build Colony still owns work/evidence policy, and General Execution still cannot decide what should be integrated, promoted, or released.
