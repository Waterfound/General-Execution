# v0.0.13 — Vercel Sandbox Conformance Runner

## Goal

Provide a provider-specific environment for General Execution's own regression bank without turning Vercel into a General Execution production transport.

The runner answers one narrow question:

> Did this exact General Execution Git revision compile and pass its committed test bank inside the fixed externally hosted Sandbox environment?

It does not decide engineering correctness beyond the committed bank, authorize retries, verify a Build Colony package, integrate code, or release anything.

## Frozen input

`VercelSandboxConformanceSpec` accepts one meaningful variable: an exact 40-character lowercase Git SHA.

Protocol-fixed values:

- repository: `https://github.com/Waterfound/General-Execution.git`;
- Vercel Sandbox runtime: `node24`;
- timeout: `300000 ms`;
- Python interpreter after provisioning: `python3.13`;
- complete command sequence.

A caller cannot supply a repository, runtime, executable, argv, command list, or shell fragment.

## Why `node24` provisions Python 3.13

The original candidate assumed the direct Vercel `python3.13` Sandbox could run the complete bank. Real execution disproved that assumption in two bounded attempts:

1. editable install with `--no-build-isolation` failed because `setuptools.build_meta` was not already present;
2. ordinary PEP 517 build isolation fixed installation and `compileall`, but pytest collection failed because the direct image lacked the native `_sqlite3` extension used by General Execution's durable stores.

A `node24` Sandbox probe showed working SQLite but a system Python 3.9.25, below General Execution's `>=3.11` requirement. Its Amazon Linux package repositories exposed supported Python 3.11/3.12/3.13 packages.

The resulting fixed failure domain is therefore:

```text
node24 Sandbox
  -> provision Python 3.13 from the image package repository
  -> prove sqlite3 availability
  -> install GE dev environment
  -> compileall
  -> full pytest
```

This is evidence-driven environment selection, not a relaxation of the protocol.

## Protocol-fixed commands

The runner executes exactly:

```text
1. git rev-parse HEAD
2. sudo dnf -y -q install python3.13 python3.13-pip
3. python3.13 -c "import sys, sqlite3; print(sys.version); print(sqlite3.sqlite_version)"
4. python3.13 -m pip install -e .[dev] --disable-pip-version-check
5. python3.13 -m compileall -q src
6. python3.13 -m pytest -q
```

The first command must exit zero and return the requested SHA exactly. Any nonzero command stops later stages.

The SQLite probe is deliberately explicit: package installation and tests are not allowed to proceed in an environment that cannot import the standard-library `sqlite3` module.

## Sandbox creation

The default backend creates a Vercel Sandbox with:

- runtime `node24`;
- exact Git source URL;
- exact requested revision;
- bounded timeout;
- optional team/project/token provider configuration when supplied.

Provider credentials never enter the returned run artifact.

On Vercel-hosted callers, provider authentication can be supplied by Vercel's environment/OIDC path rather than embedding a token in General Execution evidence.

## Stable provider identity

A successful run requires a non-empty provider-issued Sandbox identity.

Current Vercel SDKs expose the unique Sandbox identity primarily as `name`. Older SDK generations exposed id-shaped fields. `_sandbox_id()` therefore recognizes, in order:

- `name`;
- `sandbox_id`;
- `sandboxId`;
- `id`.

This is compatibility across provider SDK generations, not caller-controlled identity. An object exposing none of these stable non-empty fields is rejected and still receives a shutdown attempt.

## Provenance

Each fixed command produces `SandboxCommandEvidence` containing:

- fixed command ID;
- exact executable;
- exact argv;
- exit code;
- stdout digest;
- stderr digest.

`VercelSandboxConformanceRun` additionally binds:

- conformance spec ID/digest;
- provider identity;
- stable Sandbox identity;
- exact requested and observed Git revisions;
- fixed runtime;
- ordered command evidence;
- optional provider team/project identifiers;
- revision-verification state;
- shutdown state and shutdown-error digest;
- final `all_passed` verdict.

`all_passed=true` requires:

- exact revision verification;
- all six fixed commands recorded;
- all six exit codes equal zero;
- successful Sandbox shutdown.

## Fail-closed rules

The model rejects or fails closed on:

- invalid revision syntax;
- repository/runtime/timeout substitution;
- missing provider identity;
- source-revision mismatch;
- nonzero revision command even if stdout contains a plausible SHA;
- command evidence outside the exact fixed prefix;
- artificial successful-prefix truncation;
- inconsistent revision-verification claims;
- inconsistent shutdown evidence;
- inconsistent `all_passed` claims.

Provider/API exceptions remain exceptions; they are never converted into fabricated GREEN evidence.

## Authority boundary

This is conformance infrastructure only. It cannot:

- execute caller-supplied commands;
- select another repository;
- create a General Execution `LiveDispatchPermit`;
- reconcile a production provider invocation;
- authorize logical or physical retry;
- decide domain correctness;
- verify a Build Colony result;
- integrate code;
- release software.

Build Colony may coordinate the bounded external run, but retains its own evidence-verification/integration responsibilities.
