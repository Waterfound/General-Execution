# v0.0.9 — Durable Logical Session Registry

## Goal

Persist the complete logical `ExecutionSession` lifecycle so coordinator restart no longer requires a client to reconstruct whether a Session was merely bound, running, revoked, or already result-submitted.

## Lifecycle

The registry mirrors the existing pure Session protocol exactly:

```text
bound
  -> running
  -> revoked

bound
  -> revoked

running
  -> result_submitted
```

`revoked` and `result_submitted` are terminal. The registry does not introduce new state transitions.

## Transition protocol

Each `SessionRegistryTransition` binds:

- transition kind;
- monotonically increasing revision;
- logical Session ID;
- predecessor Session digest for non-register transitions;
- full source Session when applicable;
- full target Session;
- logical-result submission ID and digest for `submit_result`.

`register`, `start`, and `revoke` reproduce directly from the existing Session functions. `submit_result` is prepared only from a verified v0.0.8 `LogicalResultSubmission`.

## Append-only SQLite registry

`SQLiteSessionRegistry` adds a modular Session registry to the same filesystem-backed SQLite database used by the durable-head store.

It maintains:

- `ge_session_transitions`: append-only transition history;
- `ge_session_heads`: one current logical Session head per `(runner_id, session_id)`;
- `ge_session_registry_metadata`: independent registry schema version.

The Session registry has its own schema boundary rather than changing the base durable-head store schema.

## Compare-and-swap semantics

A non-register transition can commit only if the current Session head exactly equals its source Session, predecessor digest, and preceding revision.

Two transitions from the same logical head therefore cannot both become canonical. An exact already-committed transition can be replayed idempotently even after later transitions, but only if the entire canonical history still replays.

## Result-submission binding

A `submit_result` Session transition is accepted only when the same database contains the exact v0.0.8 pending result, reconciliation, and logical result submission.

Replay checks both payloads and SQLite metadata and requires:

```text
reconciliation
  -> PendingLogicalResult
  -> LogicalResultSubmission
  -> SessionRegistryTransition(submit_result)
  -> ExecutionSession(state=result_submitted)
```

This prevents the registry from accepting a structurally plausible `result_submitted` Session that is not backed by the durable result handoff.

## Recovery

`load_current(...)` reconstructs the canonical Session from the append-only history and verifies the head against the last transition.

`load_history(...)` replays the complete transition chain. Head-without-history, history-without-head, stale predecessor, changed runner capabilities, corrupted metadata, and broken result-handoff bindings fail closed.

## Legacy stores

Existing durable stores from v1–v3 are not retroactively assigned synthetic Session histories. Initializing the v0.0.9 registry preserves their existing durable data and starts an empty Session registry for new Sessions.

This avoids inventing historical `bound` or `running` states that were never persisted.

## Conformance bank

The repository includes 15 targeted tests covering bound registration, start/restart recovery, terminal revocation, full lifecycle replay, lost-ack idempotency after later transitions, stale predecessor rejection, durable result-handoff requirements, submitted-Session recovery, terminal result submission, competing revoke-versus-submit transitions, head/history corruption, runner-capability binding, independent Session heads, and non-synthesis of legacy Session history.

These are candidate tests; the stacked v0.0.5+ line still awaits the full historical repository regression in a complete runner environment before canonical promotion.

## Boundary

The registry persists the Session state machine already defined by General Execution. It does not select work, verify domain evidence, integrate artifacts, approve results, or release software.

## Next boundary

The next highest-value work is not another persistence primitive by default. After v0.0.9, the stacked execution lifecycle is sufficiently complete to justify a cross-layer coherence pass: prove that Session state, capacity state, durable head, reconciliation, pending result, and result submission cannot disagree after arbitrary restart boundaries.
