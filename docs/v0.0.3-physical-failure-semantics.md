# v0.0.3 — Physical Failure Semantics

## Purpose

v0.0.3 makes provider/transport failure part of the execution protocol instead of exceptional control flow.

The central distinction is:

```text
logical Session attempt != physical provider attempt
```

A logical Session can survive multiple failed physical attempts. Every physical attempt is independently authorized, observed, receipted, and recorded.

## Terminal transport statuses

The physical layer recognizes exactly five terminal statuses:

- `completed`
- `rejected`
- `timed_out`
- `cancelled`
- `transport_failed`

`completed` requires a bound `ResultEnvelope` and a concrete provider invocation identity. Failure statuses cannot carry a result and require a failure code. `transport_failed` may legitimately have no provider invocation identity when the failure happened before the provider allocated one.

## PhysicalAttemptAuthorization

An initial physical attempt has:

- `physical_attempt = 1`
- no predecessor invocation
- no predecessor receipt

A retry has:

- `physical_attempt = prior + 1`
- a new request/invocation identity
- `previous_invocation_id = prior invocation`
- `previous_receipt_digest = digest(prior receipt)`

This makes retries append-only. They cannot overwrite or reinterpret a prior attempt.

## PhysicalObservation

A provider/transport observation is bound to:

- authorization ID and digest;
- exact request and invocation;
- physical attempt ordinal;
- provider invocation identity when available;
- terminal transport status;
- result or failure code;
- optional detail digest.

The response digest covers the complete observation payload.

## PhysicalReceipt

The coordinator emits a receipt only after admitting the observation. The receipt commits to the authorization, predecessor lineage, provider identity, terminal status, observation digest, response digest, and either result digest or failure code.

## Retry semantics

Failure does not mutate the logical Session. The caller may:

- authorize another physical attempt; or
- explicitly revoke the logical Session.

The core does not decide retry policy. It only makes retry history exact and auditable.

Retry after `completed` is rejected.

## Duplicate physical attempts

A duplicated provider delivery or accidental second physical execution of the same authorization is not converted into a retry and is not allowed to overwrite the canonical attempt.

When two distinct provider invocation IDs bind to the same physical authorization, the coordinator can emit `DuplicatePhysicalAttempt` evidence containing both observation digests and both provider invocation IDs.

## Ledger

Every canonical physical attempt occupies exactly four events:

```text
PHYSICAL_DISPATCH
PHYSICAL_OBSERVATION
PHYSICAL_RECEIPT
PHYSICAL_RESULT | PHYSICAL_TERMINAL_FAILURE
```

Attempt re-recording is rejected by authorization digest.

Duplicate evidence uses a separate `DUPLICATE_PHYSICAL_ATTEMPT` event and therefore cannot masquerade as a second canonical physical attempt.

## Authority boundary

Transport completion is not domain verification.

General Execution may establish that a result belongs to the exact authorized logical Session and physical attempt. It still cannot declare the result correct, integrate it, release it, alter a project profile, or inherit Build Colony governance.

## Local conformance gate

The v0.0.3 gate requires:

- all v0.0.1/v0.0.2 published tests remain green;
- all terminal failure statuses are representable and verifiable;
- failure does not close the logical Session;
- retry lineage is predecessor-bound;
- retry after completion fails closed;
- tampered observations and result bindings fail closed;
- retry-chain tampering fails closed;
- duplicate physical executions become explicit evidence;
- physical-attempt ledger records replay exactly;
- repeated canonical recording is rejected;
- package compiles and installs without runtime dependencies.
