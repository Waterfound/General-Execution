# v0.0.9 — Reattachable Reference Provider

## Goal

Provide the first concrete provider-side control-plane implementation of the v0.0.8 reattachment protocol without adding workload execution to General Execution.

## Architecture

v0.0.9 intentionally separates two layers:

1. `SQLiteReferenceJobRegistry` stores durable provider-key identity and provider-side status.
2. `reference_bridge.py` translates General Execution protocol objects into registry operations and translates registry state back into `ProviderStatusObservation` objects.

The registry does not understand `ExecutionSpec`, capacity, reconciliation, or domain evidence. The bridge does not run commands or workloads.

## Deterministic identity

During the original provider registration, `register_reference_invocation(...)` derives the v0.0.8 client-generated `ProviderReattachmentKey` from the exact physical authorization.

The registry derives one deterministic reference `job_id` from that provider key. Repeating the same registration returns the same job identity and is idempotent.

This gives the coordinator an identity that can be reconstructed after restart without depending on a provider-assigned identifier having been persisted before a crash.

## Durable registry

The reference registry uses filesystem-backed SQLite with WAL journaling and `synchronous=FULL`.

Each provider key maps to one immutable binding digest and one deterministic job ID. The state is either:

- `running`; or
- `terminal`, with one immutable terminal payload and its digest.

Concurrent registration of the same provider key converges on one job identity. A later attempt to map the same key to a different binding is an integrity failure.

## Status bridge

`query_reference_status(...)` converts registry state into v0.0.8 status observations:

- absent key -> `not_found`;
- running record -> `running` with the deterministic job ID;
- terminal record -> `terminal` with the persisted `PhysicalObservation`.

The bridge verifies terminal-payload integrity and that the persisted physical observation carries the same deterministic job ID.

The strong physical verification still happens later in v0.0.8 through `assess_provider_status(...)` and `admit_physical_observation(...)`.

## Terminal recording

`record_reference_terminal(...)` is a reference-provider simulation hook. It records a terminal physical observation only when authorization ID, invocation ID, and deterministic job ID all match the registered provider key.

Exact replay of the same terminal payload is idempotent. A different terminal payload cannot replace the first canonical terminal payload.

## End-to-end recovery path

```text
physical authorization
  -> deterministic provider_key
  -> reference registry: running
  -> coordinator restart
  -> recovered in_flight_unknown lease
  -> same provider_key reconstructed
  -> registry query: running / not_found / terminal
  -> v0.0.8 status admission
  -> PhysicalOutcomeBundle when terminal
  -> v0.0.7 reconciliation
```

No redispatch is required for reattachment.

## Authority boundary

The reference provider is a provider/control-plane simulator only. It does not execute shell commands, arbitrary processes, or user workloads. It does not release capacity, submit logical Session results, verify application-domain evidence, integrate changes, or make release decisions.

The SQLite registry makes provider identity and status durable; it does not make those claims authoritative. Protocol admission remains outside the registry.

## Conformance bank

The v0.0.9 tests cover registration and reopen, deterministic/idempotent job identity, absent-key `not_found`, persisted terminal status feeding v0.0.8 and v0.0.7, exact terminal replay, conflicting terminal rejection, wrong-job rejection, concurrent registration convergence, registry schema validation, filesystem-only persistence, capability gating, and preservation of terminal state across repeated registration.

## Next boundary

After the stacked v0.0.5-v0.0.9 line is admitted, the next high-value milestone is an **end-to-end restart rehearsal** joining durable capacity head, provider registry, coordinator restart, provider reattachment, terminal observation, reconciliation, and optional explicit Session result submission in one deterministic scenario.
