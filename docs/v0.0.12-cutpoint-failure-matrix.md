# v0.0.12 — Cross-Store Cut-Point Failure Matrix

## Goal

Turn the recovery ordering from v0.0.11 into executable crash-boundary evidence across the three durable stores:

1. recovery-context store;
2. canonical capacity-head store;
3. provider identity/status registry.

The matrix does not infer safety from elapsed time. It reconstructs the exact state from durable records after each cut point.

## Canonical cut points

The reference matrix freezes five durable boundaries:

```text
context_persisted
capacity_committed
provider_registered
terminal_persisted
reconciliation_committed
```

Each boundary is prepared in fresh stores and then assessed through a separate stores-only path.

## Expected states

| Cut point | Restart classification | Meaning |
| --- | --- | --- |
| `context_persisted` | `orphan_context` | context is durable but no canonical capacity head exists; nothing is active |
| `capacity_committed` | `active_provider_unknown` | lease is canonical, provider key is absent / `not_found`, occupancy remains active |
| `provider_registered` | `active_provider_running` | exact provider identity exists and running status preserves occupancy |
| `terminal_persisted` | `terminal_pending_reconciliation` | terminal physical outcome is reconstructable but capacity is still occupied |
| `reconciliation_committed` | `settled_terminal_reconciliation` | lease is released and the canonical release matches the durable terminal outcome |

## Conservative `not_found`

A crash after capacity commit but before provider registration leaves a recoverable active lease and no provider record.

The assessor deliberately maps this to:

```text
not_found -> remain_unknown
```

It does **not** fabricate transport failure, release capacity, or authorize retry.

This preserves the v0.0.8 rule that provider lookup failure is not evidence that work never started.

## Lost reconciliation acknowledgement

The final cut point models a coordinator crash after the reconciliation CAS succeeded but before the caller retained the in-memory receipt.

At that point the recovered lease is no longer active, so ordinary active cold bootstrap intentionally ignores its historical context.

`assess_reference_cutpoint(...)` handles this by using the immutable recovery-context anchor plus the current canonical capacity history and durable provider terminal evidence. It proves:

- current capacity history extends the anchor prefix;
- exactly one canonical release exists for the bound lease;
- the provider still exposes the terminal observation for the exact authorization;
- physical-outcome admission reproduces the same `outcome_digest`;
- the canonical release carries that exact outcome digest and physical receipt digest.

Only then is the state classified as `settled_terminal_reconciliation`.

This makes a lost post-CAS acknowledgement observable without reopening the lease or fabricating another execution.

## Invalid ordering

The matrix fails closed if durable provider identity exists while the canonical capacity head is absent. That state violates the intended persistence order because provider-side lifecycle must not begin before coordinator-side recoverability exists.

The intended order remains:

```text
recovery context
  -> capacity head
  -> provider identity
  -> provider terminal state
  -> reconciliation CAS
```

## Reconciliation source

For the `reconciliation_committed` fixture, the terminal provider state is reconciled through a cold binding reconstructed from the stores. The preparation-side Spec / registry / Session / authorization objects are not reused for the reconciliation commit.

## Authority boundary

The cut-point matrix is QA evidence. It does not grant retry authority, application verification authority, integration authority, or release authority.

A settled physical reconciliation still does not imply logical result submission:

```text
physical completion != logical result submission
```

## Conformance bank

The v0.0.12 tests cover all five canonical cut-point classifications, safe orphan behavior, conservative provider `not_found`, terminal persistence without premature capacity release, post-CAS lost-ack reconstruction, invalid provider-before-capacity ordering, terminal-payload corruption rejection, and deterministic assessment across fresh filesystem paths.

## Admission boundary

v0.0.12 remains stacked above the v0.0.5-v0.0.11 candidate line. The matrix is targeted protocol evidence; it does not substitute for the full historical repository regression.

## Next boundary

After the cut-point matrix is frozen, the next highest-value question is **durable logical Session settlement**. Physical completion and capacity reconciliation survive cold restart, but a later explicit `submit_result(...)` still changes only an in-memory `ExecutionSession`. A crash around logical result submission therefore needs its own durable, idempotent settlement protocol before the execution lifecycle can be considered end-to-end crash complete.
