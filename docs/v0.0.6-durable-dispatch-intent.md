# v0.0.6 — Durable Dispatch Intent & Ambiguity Recovery

General Execution v0.0.6 closes the coordinator crash window between an active capacity lease and a future external provider submission.

## Problem

v0.0.5 can durably recover an active capacity lease, but a restart alone cannot answer a different question:

> Did the external provider receive this invocation before the coordinator crashed?

Treating that ambiguity as a failure and blindly re-submitting could duplicate physical work. Treating it as success would fabricate provider evidence.

v0.0.6 therefore makes dispatch intent durable before concrete remote transport exists.

## Durable state machine

Each active physical authorization may have one durable dispatch intent bound to the exact:

- runner and capability digest;
- capacity lease ID and digest;
- slot;
- Session and logical attempt;
- physical authorization ID and digest;
- invocation ID and request digest;
- physical-attempt ordinal;
- capacity-state digest at intent creation.

The durable state machine is:

```text
PREPARED
  -> SUBMISSION_UNKNOWN
  -> OBSERVED
```

### PREPARED

The intent is durable, but General Execution has not authorized transport to treat submission as begun.

Restart action: `begin_submission`.

The transition itself still revalidates that the bound capacity lease is active.

### SUBMISSION_UNKNOWN

This state is committed before a future provider side effect is allowed. It means:

> the durable system must now assume submission may occur or may already have occurred.

Restart action: `reconcile_provider`.

It does **not** authorize blind re-submission and does not infer a provider outcome.

### OBSERVED

A native `PhysicalOutcomeBundle` has been admitted and bound to the exact durable intent.

Restart action: `none`.

Late provider evidence remains recordable even if the owning Session was subsequently revoked; evidence recording is not new execution authority.

## Two permit layers

v0.0.6 deliberately distinguishes two artifacts.

### `DispatchPermit`

`DispatchPermit` proves that the durable outbox reached `SUBMISSION_UNKNOWN`. It is a durable transition proof, not by itself sufficient authority for a future transport implementation.

### `LiveDispatchPermit`

A future transport must require `LiveDispatchPermit`.

It can only be derived when:

1. the durable dispatch state is still `SUBMISSION_UNKNOWN`;
2. the `DispatchPermit` reproduces exactly;
3. the current capacity state replays for the exact runner;
4. the original lease is still active and reproduces every Session / authorization / invocation binding.

The live permit additionally binds the exact current capacity-state digest and generation.

Therefore:

- Session revocation + capacity release invalidates an already-issued live permit;
- terminal outcome + capacity release invalidates an already-issued live permit;
- even an unrelated capacity generation change makes an old live permit stale and requires a fresh authorization check.

This is intentional fail-closed behavior.

## Restart recovery

`recover_dispatch_after_restart()` never invents transport facts.

For each durable intent it returns exactly one recovery action:

| Durable state | Recovery action | Blind resubmit? | Provider outcome inferred? |
| --- | --- | --- | --- |
| `prepared` | `begin_submission` | no | no |
| `submission_unknown` | `reconcile_provider` | no | no |
| `observed` | `none` | no | no |

The recovery report itself carries zero authority to submit work.

## Durable storage

`SqliteDispatchIntentStore` uses standard-library SQLite and transactional compare-and-swap transitions.

The store enforces:

- one durable dispatch intent per capacity lease;
- one canonical revision per intent;
- exact predecessor-state digest binding;
- stale writer rejection;
- row metadata reconciliation against deserialized state;
- no state transition that changes immutable intent identity.

## v0.0.6 conformance target

The candidate test bank covers:

- restart while `PREPARED`;
- restart while `SUBMISSION_UNKNOWN`;
- no blind resubmission under ambiguity;
- exact live-permit binding to current capacity state;
- live-permit invalidation after Session revocation/capacity release;
- live-permit refresh after unrelated capacity generation change;
- stale begin-submission CAS rejection;
- admitted provider outcome transition to `OBSERVED`;
- terminal restart recovery after `OBSERVED`;
- durable row metadata tampering;
- serialized state tampering;
- live permit tampering.

## Remaining distributed boundary

A local database cannot make a transaction atomic with an arbitrary remote provider side effect. v0.0.6 therefore intentionally does **not** add concrete remote transport.

The next ceiling is a provider reconciliation / idempotency contract that can answer, using the stable invocation identity, whether an ambiguous invocation is absent, accepted/running, or terminal — without blind duplicate submission.

Only after that contract is proven should a real remote adapter be allowed to consume `LiveDispatchPermit`.

## Authority invariant

> Durable ambiguity is preserved as ambiguity until provider evidence resolves it.

General Execution may remember and reconcile execution state. It does not create permission to build, verify, integrate, promote, or release project changes.
