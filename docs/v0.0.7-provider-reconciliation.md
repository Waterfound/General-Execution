# v0.0.7 — Provider Idempotency & Reconciliation

General Execution v0.0.7 defines the provider-neutral contract required to resolve a durable `SUBMISSION_UNKNOWN` state without turning uncertainty into blind duplicate work.

## Problem

v0.0.6 persists submission ambiguity before any future remote side effect. After a restart, however, General Execution still needs a provider-facing protocol that can answer what happened to one exact physical invocation.

The reconciliation key is the existing stable `invocation_id`, bound to the exact request digest. Reconciliation never creates a new physical-attempt identity.

## Provider contract

`ProviderReconciliationContract` binds the exact provider, adapter and adapter version and declares:

- lookup by `invocation_id`;
- request-digest binding;
- same-key / same-request semantics;
- mandatory rejection of same-key / different-request submission;
- whether terminal provider evidence can be retrieved.

Supported same-key / same-request semantics are:

- `same_operation` — duplicate submit resolves to the same provider operation;
- `duplicate_rejected` — duplicate submit is rejected without creating a second operation;
- `may_duplicate` — the provider can reconcile but cannot safely support automatic re-submission.

Only the first two are eligible for `safe_idempotent_resubmission`.

## Reconciliation query

A `ProviderReconciliationQuery` can only be created from a durable dispatch state that is still `SUBMISSION_UNKNOWN` and whose non-authoritative `DispatchPermit` reproduces exactly.

The query binds:

- dispatch intent and state digest;
- dispatch permit digest;
- physical authorization ID and digest;
- invocation ID and request digest;
- physical-attempt ordinal;
- runner identity;
- provider / adapter / adapter version;
- provider reconciliation contract digest.

The physical authorization must reproduce the durable dispatch intent before the query is emitted.

## Provider statuses

A provider reconciliation observation reports exactly one of:

| Status | Meaning | Automatic re-submit? |
| --- | --- | --- |
| `absent` | provider asserts the invocation is not present | only under strong idempotency + fresh live permit |
| `accepted` | provider recognizes an existing operation | no; poll existing operation |
| `terminal` | provider recognizes a terminal operation | no; admit terminal evidence when retrievable |
| `unknown` | provider cannot establish state | no; preserve ambiguity |

Every observation binds the query digest, invocation ID, request digest and exact provider identity. Terminal evidence requirements are checked against the contract.

## Decision policy

`decide_reconciliation()` re-creates the query and re-admits the provider observation before making a decision. Constructing an `Evidence` object manually therefore does not bypass identity checks.

### ABSENT

`ABSENT` is not by itself transport authority.

Automatic re-submission of the **same invocation ID** is authorized only when all of the following hold:

1. the provider contract is reconciliation-capable;
2. same-key / same-request semantics are `same_operation` or `duplicate_rejected`;
3. same-key / different-request is rejected;
4. the request digest is part of the provider idempotency contract;
5. a fresh `LiveDispatchPermit` verifies against the current canonical durable capacity head.

If the provider declares `may_duplicate`, the decision is `hold` even when the provider reports `absent`.

### ACCEPTED

Decision: `poll_existing`.

The provider already recognizes the invocation, so submitting another operation is unnecessary.

### TERMINAL

If the contract supports retrievable terminal evidence, decision: `admit_terminal_evidence`.

If terminal state can be reported but admissible evidence cannot be retrieved, decision: `hold`.

### UNKNOWN

Decision: `hold`.

Strong idempotency does not turn an unknown provider state into automatic retry. Ambiguity remains ambiguity until provider evidence resolves it.

## Retry distinction

Re-sending an ambiguous invocation under the exact same `invocation_id` is not the same operation as `authorize_retry()`.

- reconciliation re-submit preserves the same physical-attempt identity and relies on provider idempotency;
- native retry creates a new physical invocation only after an admitted terminal non-completed outcome.

The two paths must never be conflated.

## Current safety boundary

v0.0.7 defines and validates reconciliation logic but intentionally does not ship a concrete remote provider adapter.

A `ProviderReconciliationContract` is still a capability declaration, not proof that a real adapter/provider satisfies the promise. Production transport must therefore remain gated until a conformance harness can independently prove the contract properties and bind that evidence to the exact adapter revision.

## v0.0.7 conformance target

The focused test bank covers:

- stable invocation/request identity binding;
- wrong-provider contract rejection;
- lookup/request-binding capability rejection;
- safe ABSENT re-submit with fresh live permit;
- unsafe `may_duplicate` ABSENT hold;
- missing live-permit rejection;
- stale live-permit rejection after revocation;
- ACCEPTED -> poll existing;
- TERMINAL -> evidence admission;
- TERMINAL without evidence lookup -> hold;
- UNKNOWN -> hold even with strong idempotency;
- observation identity mismatch rejection;
- manual evidence forgery revalidation;
- invalid same-key / different-request contract rejection.

## Next ceiling

The next highest-value boundary is **provider reconciliation conformance & attestation**.

A candidate provider adapter should not become transport-eligible merely by declaring `same_operation` or `duplicate_rejected`. General Execution should independently exercise duplicate submission, same-key/different-request rejection, lookup identity binding, absence semantics and terminal evidence retrieval, then emit an attestation bound to the exact contract and adapter revision.

Only an attested contract should eventually be consumable by concrete remote transport.

## Authority invariant

> Provider reconciliation may resolve execution ambiguity; it does not create project authority.

General Execution still cannot decide what should be built, whether evidence is sufficient for integration, or whether anything should be promoted or released.
