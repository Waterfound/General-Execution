# v0.0.11 — Deterministic Session Recovery Projection

## Goal

Recover the logical `ExecutionSession` state after coordinator restart without introducing a second durable Session database when the existing durable execution evidence already determines that state.

v0.0.11 is a convergence result. A parallel prototype explored an append-only Session registry. After integrating the canonical v0.0.6–v0.0.10 dispatch/provider path, a smaller solution became available: project the Session from durable capacity history, dispatch state, and complete observed outcomes.

## Principle

Do not persist state that can be reproduced exactly from more authoritative durable evidence.

```text
ExecutionSpec + Registry + Plan
            |
            v
     deterministic bound Session
            |
            +-------------------------------+
            |                               |
            v                               v
 durable capacity history          durable dispatch/outcome
            |                               |
            +---------------+---------------+
                            |
                            v
               SessionRecoveryProjection
```

## Projection classes

A projection is classified as:

- `coherent` — durable evidence determines a stable logical state;
- `recovery_required` — durable evidence determines both the current logical state and one mechanical recovery step still pending;
- `legacy_untracked` — an older durable path lacks bytes required for safe reconstruction, so no state is invented;
- `inconsistent` — durable layers encode a combination that should not be advanced.

`SessionRecoveryProjection` binds the projected Session and its digest to the canonical capacity state/head, physical transition count, latest physical-attempt ordinal, active lease, dispatch state, durable outcome, last release, retry eligibility, and bounded recovery action.

## Restart ladder

### No physical history

The only durable fact is the deterministic `bound` Session. The projection returns:

```text
bound
recovery_action = start_session
```

If the Session had previously been started only in memory and crashed before creating durable physical state, replaying `start_session(bound)` is safe and deterministic.

### Active capacity lease, no dispatch intent

The logical Session is `running`. Capacity proves that physical authorization reached the reservation boundary, but the durable outbox is not yet present.

```text
running
recovery_action = prepare_dispatch_intent
```

The projection does not fabricate the missing intent.

### Prepared dispatch

```text
running
recovery_action = begin_submission
```

### Submission unknown

```text
running
recovery_action = reconcile_provider
```

No blind resubmission is authorized by the projection.

### Observed dispatch with active capacity

The v0.0.10 complete outcome bytes are present, but the capacity lease is still active.

```text
running
recovery_action = release_observed_capacity
```

The existing v0.0.10 release recovery performs the exact verified release.

## Terminal capacity history

### Session-revoked release

`release_capacity_for_revocation()` already binds the digest of the exact revoked Session. v0.0.11 reconstructs `revoke_session(running)` and requires its digest to equal the durable release binding.

The projected state is therefore:

```text
revoked
```

No separate Session row is required.

### Completed physical outcome

A v0.0.10 terminal release plus its complete durable `PhysicalOutcomeBundle` determines the exact logical `ResultEnvelope`.

v0.0.11 reruns `verify_physical_outcome()` and then reproduces the existing pure transition:

```text
submit_result(running, durable_outcome.result)
```

The projected state becomes:

```text
result_submitted
```

This works for either a successful or failed logical `ResultEnvelope`; transport completion and logical result status remain distinct concepts.

### Failed physical transport

A terminal failure release does not end the logical Session. With the exact durable prior outcome present, the projection is:

```text
running
retry_eligible = true
```

`retry_eligible` is evidence, not retry authority. General Execution does not decide whether the caller should retry or revoke.

## Retry chains

Capacity history carries physical-attempt ordinals and predecessor bindings. If attempt 1 fails and a later attempt 2 is already active, the projection selects the active attempt and reports its exact physical-attempt ordinal.

The Session remains the same logical attempt while physical retries advance independently.

## Legacy behavior

A terminal outcome release created before v0.0.10 may contain outcome/receipt hashes without the complete physical outcome bytes.

v0.0.11 does not reconstruct a result or authorize retry from hashes alone. It returns `legacy_untracked` with `retry_eligible = false`.

This preserves the fail-closed evidence rule introduced during convergence.

## What is deliberately not persisted

v0.0.11 does not add:

- a Session heads table;
- a Session transition ledger;
- a second source of truth for `bound/running/revoked/result_submitted`;
- automatic retry policy;
- domain verification or integration decisions.

The projected Session is a deterministic view over the durable execution facts already required for safe provider/capacity recovery.

## Conformance bank

The candidate branch contains 10 focused tests covering:

- no-history bound/start projection;
- active lease without dispatch intent;
- prepared dispatch;
- submission-unknown dispatch;
- observed outcome awaiting capacity release;
- failed terminal release and retry eligibility;
- completed terminal release reconstructing `result_submitted`;
- revocation release reconstructing `revoked`;
- legacy terminal release without complete outcome bytes;
- physical retry attempt 2 with an active lease.

The bank is committed as candidate evidence. No 10/10 execution claim is made until the stacked branch is available in a runnable environment without consuming GitHub Actions quota.

## Authority boundary

The projection reports what durable execution evidence proves. It does not decide what should be built, whether provider output is correct at the domain level, whether a retry should occur, or whether a result should be integrated or released.

> Execution consumes authority. It does not create authority.

## Next boundary

After executable regression, the next useful convergence step is a bounded recovery driver that consumes only `recovery_required` projections and applies the named mechanical transition. It must refuse `legacy_untracked` and `inconsistent` projections and must not convert `retry_eligible` into automatic retry policy.
