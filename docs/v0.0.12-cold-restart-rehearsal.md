# v0.0.12 — Cold Coordinator Reconstruction Rehearsal

## Goal

Exercise the recovery stack after volatile coordinator protocol objects are discarded.

Unlike v0.0.10, the resume phase receives no `ExecutionSpec`, registry, plan, Session, runner object, or physical authorization from its caller. It receives only filesystem paths to three durable stores.

## Two-phase boundary

The rehearsal is split deliberately:

```text
prepare_reference_cold_restart(...)
  -> persist immutable recovery context
  -> persist canonical capacity head
  -> persist provider identity
  -> return only a preparation receipt

resume_reference_cold_restart(...)
  -> receive only capacity/context/provider paths
  -> bootstrap active recovery context
  -> reconstruct runner + Spec + registry + plan + Session + authorization
  -> query provider status
  -> admit physical outcome
  -> reconcile capacity
```

The second function cannot consume caller-retained protocol objects because they are absent from its interface.

## Safe preparation order

Preparation uses the v0.0.11 fail-safe order:

```text
recovery context
  -> capacity head
  -> provider registration
```

A crash before the capacity commit leaves only an orphan context. A crash after the capacity commit but before provider registration leaves a recoverable occupied lease whose provider state may be `not_found`; it does not create permission to retry or release automatically.

## Cold bootstrap

The resume phase invokes `bootstrap_active_recovery_contexts(...)`.

The recovery-context store reconstructs the runner definition from its self-contained anchor context. The capacity store is then replayed with that runner definition, and only an exact still-active recovered lease becomes a cold recovery binding.

The recovered context supplies the typed objects used by the existing protocols:

- `ExecutionSpec`;
- `RunnerRegistry`;
- `DispatchPlan`;
- running `ExecutionSession`;
- `PhysicalAttemptAuthorization`.

No new substitute recovery semantics are introduced.

## Provider status and reconciliation

After bootstrap, provider `running` must still assess as `keep_running` with no physical outcome.

The reference rehearsal then records either:

- `timed_out`, producing no logical result; or
- `completed`, producing a `ResultEnvelope`.

Terminal state passes through v0.0.8 physical admission and v0.0.7 reconciliation. Capacity is released only by that canonical reconciliation path.

Even after physical completion, the reconstructed Session remains `running`. `submit_result(...)` remains a distinct explicit operation.

## Context mode

Every v0.0.12 report freezes:

```text
context_mode = cold_reconstructed
```

This distinguishes it from v0.0.10's `caller_retained` store-reopen evidence.

## Authority boundary

The rehearsal reconstructs identity and recovery state. It does not authorize new work, infer provider failure from silence, verify domain evidence, integrate changes, approve releases, or automatically submit a logical result.

## Conformance bank

Tests cover cold timeout recovery, cold completion with explicit later result submission, preparation receipts spanning all three durable layers, deterministic replay across fresh filesystem paths, distinct-store enforcement, invalid terminal mode handling, and rejection of a second resume after the recovered lease has already been canonically reconciled.

## Evidence boundary

v0.0.12 proves a protocol-level cold reconstruction boundary through APIs that do not carry volatile protocol objects into resume. It is not yet an operating-system process-separation test and does not replace the still-pending full historical repository regression.

## Next boundary

The next highest-value step is a **restart cut-point matrix** around the three-store protocol: context persisted only, capacity committed before provider identity, provider running, terminal persistence, and reconciliation CAS. Each cut point should converge to one explicit safe recovery state with no duplicate canonical execution.
