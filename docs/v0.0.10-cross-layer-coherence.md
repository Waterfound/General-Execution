# v0.0.10 — Cross-Layer Coherence

## Goal

Prove that the independently developed execution layers cannot silently disagree after arbitrary coordinator restart boundaries.

The layers checked together are:

```text
logical Session registry
        x
capacity / lease history
        x
durable capacity head
        x
provider reconciliation
        x
pending logical result
        x
logical result submission
```

The milestone does not introduce new domain authority. It classifies protocol state and blocks unsafe lifecycle commits.

## Coherence status

`ExecutionCoherenceReport` classifies one logical Session as one of four states:

- `coherent` — the durable layers agree;
- `recovery_required` — the state is valid but one known mechanical catch-up transition remains;
- `legacy_untracked` — execution state predates the durable Session registry and must not receive invented history;
- `inconsistent` — the layers encode a combination that cannot safely be advanced.

The report binds runner, Session, logical attempt, durable head, matching capacity-transition count, active lease IDs, pending-result identity, submission identity, findings, and required recovery actions.

## Physical-history recovery

A `bound` Session with physical history is not automatically corruption. It can represent a crash after the in-memory `start` transition but before the durable Session-registry update.

This includes both:

- an active physical lease; and
- completed reserve/release history with no currently active lease.

The required recovery action is `COMMIT_START_SESSION_TRANSITION`.

A missing Session registry with pre-existing capacity history remains `legacy_untracked`; v0.0.10 does not synthesize a historical registration.

## Revocation ordering

Capacity release caused by explicit Session revocation may be committed before the durable Session-registry transition if the coordinator crashes between the two operations.

A running Session with a canonical `session_revoked` capacity release is therefore classified as `recovery_required` with action `COMMIT_REVOKE_SESSION_TRANSITION`.

The coherent Session registry still refuses to persist a revoked logical Session while an active lease exists. Capacity must be released first.

## Completed-result fail-closed rule

A terminal physical release with transport status `completed` is not sufficient evidence to reconstruct a logical result. The release contains digests, not the complete `ResultEnvelope`.

Therefore a completed physical release with no durable pending-result handoff is `inconsistent` and cannot be converted into a logical revocation or fabricated result.

This preserves the existing principle that evidence bytes, not memory or hashes alone, decide the logical handoff.

## Atomic Session guards

`CoherentSQLiteSessionRegistry` extends the v0.0.9 registry without replacing its storage engine. Its overridden cross-layer guard runs inside the same SQLite `BEGIN IMMEDIATE` transaction used by `commit_transition`.

It adds these atomic rules:

- a new `register` cannot be placed over any existing capacity history for the same Session/attempt;
- `start` catch-up is allowed over ordinary physical history but fails closed if a completed physical release has lost its durable result handoff;
- `revoke` still requires no active capacity and additionally cannot consume a completed physical outcome as if it were revocation;
- exact idempotent replay of an already-canonical earlier transition remains allowed after later physical history appears.

## Recovery ladder

The intended restart catch-up order is mechanical and bounded:

```text
bound + physical history
    -> durable start

running + revocation release
    -> durable revoke

running + pending result
    -> durable logical-result submission

running + persisted submission
    -> durable submit_result Session transition
```

Each step moves the system toward `coherent`. No step decides whether engineering evidence is correct or whether a result should be integrated.

## Conformance bank

The repository contains 17 targeted v0.0.10 tests covering active and released physical history, start catch-up, atomic rejection of retroactive registration, legacy non-synthesis, active-capacity revocation rejection, pending/submission recovery states, coherent submitted results, direct inconsistent-state classification, orphan result state, idempotent replay after later physical history, deterministic report identity, revocation-release catch-up, and completed-release-without-handoff fail-closed behavior.

These tests are present in the candidate branch. They are not claimed as an executed 17/17 gate until the complete branch is materialized in a runnable environment.

## Boundary

Cross-layer coherence is protocol consistency, not project management, domain verification, integration approval, or release authority.

## Next boundary

After v0.0.10 and the stacked candidate line receive a complete historical regression, the next useful layer is a bounded recovery driver that consumes only `recovery_required` reports and applies one explicitly named mechanical catch-up action at a time. It must never act on `inconsistent` or `legacy_untracked` state.
