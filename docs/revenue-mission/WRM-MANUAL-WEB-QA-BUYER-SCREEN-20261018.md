## Acceptance boundary

The economically valuable predicates in the observed jobs are not merely report formatting. They include:

- access to private or pre-release application states and buyer-authored test guides;
- manual exploratory and usability judgment when requirements are limited;
- cross-browser and real-device observations;
- authenticated registration, role, cart and checkout flows;
- screenshots or recordings tied to an actual failure;
- regression verification after fixes;
- communication with the buyer and development team.

A public or synthetic fixture can prove that Waterfound can format a bug dossier. It cannot establish coverage of the buyer's private application, real-device behavior, usability judgment, or actual defect discovery. Building such a sample now would therefore answer an already-known presentation predicate rather than the buyer's acceptance predicate.

## Substitution boundary

Established tools already cover the machine-admissible layer:

- Playwright records browser actions and provides DOM snapshots, network requests, console logs and screenshots through Trace Viewer.
  Source: https://playwright.dev/
- BrowserStack Live provides interactive cross-browser testing on real devices, screenshots, session recordings, debugging and bug capture.
  Source: https://www.browserstack.com/docs/testing-toolkit/live
- TestRail can push bug reports to Jira, link issues to test results and track requirement coverage and traceability.
  Source: https://support.testrail.com/hc/en-us/articles/7665131077268-Connect-to-Jira-Cloud

Waterfound has not observed a buyer requesting provenance, autonomous recovery, governed authority stops or cross-system mission state as the differentiating job. A generic evidence ledger or dashboard would therefore duplicate mature testing and issue-management substitutes without demand evidence.

## Decision

Do not build a web QA scanner, generic bug-report generator, screenshot ledger, test-management dashboard, browser farm, or synthetic sample merely to support these listings.

Keep manual web QA as a **buyer-evidence channel**, not the active product wedge. Re-enter only when all are true:

1. the canonical listing is directly reachable and currently open;
2. the buyer's target, permitted actions and acceptance fields are explicit before contact;
3. a public or synthetic proof can retire a named acceptance risk without pretending to test private flows;
4. the buyer values a specific gap not already satisfied by Playwright, BrowserStack, TestRail, Jira or native issue trackers;
5. required browsers/devices, accounts and test data are available without new spend or unauthorized access;
6. price and competition justify the manual verification burden;
7. Waterfound separately authorizes any application, outreach, account action, customer access, contract, payment/KYC or publication.

## Kill criteria

Reject before build if any one holds:

- the listing cannot be reconciled as currently open from its canonical page;
- acceptance depends on private staging access, buyer credentials or test guides not yet authorized;
- checkout, payment, account creation or destructive state changes are required for the proof;
- real-device or browser coverage is unavailable inside the existing no-spend envelope;
- the deliverable is primarily manual usability judgment rather than a bounded machine-verifiable predicate;
- native or established tools already produce the requested artifact with no observed gap;
- a synthetic fixture would demonstrate formatting only;
- the opportunity requires outreach or platform application before scope can be bounded.
