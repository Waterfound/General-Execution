# v0.0.5 — Durable Head & Restart Recovery

General Execution v0.0.5 makes runner capacity state restart-safe without changing who owns execution authority or inventing provider outcomes.

## Problem

v0.0.4 made capacity transitions deterministic and replayable in memory, but the canonical head was not durable. A coordinator restart could therefore lose which physical leases were still occupying runner slots.

The critical failure to avoid is optimistic recovery: treating an in-flight physical attempt as failed, completed, or released merely because the coordinator restarted.

## Durable head

`SqliteCapacityHeadStore` persists one canonical `RunnerCapacityState` head per runner using Python's standard-library SQLite implementation.

Each stored head binds:

- runner ID;
- exact runner capability digest;
- capacity-state digest;
- generation;
- snapshot digest;
- canonical serialized snapshot.

State commits run inside `BEGIN IMMEDIATE` and require the caller's `expected_state_digest` to equal the current durable head. A commit must extend the stored transition history by exactly one generation and bind its `previous_state_digest` to the current head.

This preserves the v0.0.4 compare-and-swap rule across process restarts and competing store connections.

## Snapshot verification

A durable snapshot is not trusted because it was read from SQLite. Reload performs all of the following:

1. verify snapshot schema and snapshot digest;
2. reconstruct every lease, release, and transition as native immutable capacity objects;
3. verify the reconstructed state digest;
4. replay the full state against the exact `RunnerCapabilities`;
5. reconcile persisted row metadata with the reconstructed state.

Capability drift, history tampering, metadata tampering, malformed snapshots, and non-replayable state therefore fail closed.

## Restart recovery

`recover_capacity_after_restart()` reloads the verified durable head and produces a `RestartRecoveryReport`.

Every active lease is reported as:

```text
status = in_flight_unresolved
physical_outcome_fabricated = false
capacity_released = false
```

The recovered state keeps the same slot occupied. With `max_parallelism = 1`, another logical Session therefore remains blocked until one of two target-authorized facts arrives:

- a real physical observation is admitted and the corresponding outcome release is committed; or
- the owning Session is explicitly revoked and the existing revocation release path is committed.

Coordinator restart alone is never evidence of provider failure or completion.

## Atomicity boundary

SQLite is used here because the core requires a real atomic compare-and-swap boundary, not a best-effort JSON-file convention. The implementation uses no non-stdlib runtime dependency.

The store is intentionally narrow: it owns the canonical capacity head, not provider transport, Session authority, evidence verification, integration, or release decisions.

## v0.0.5 conformance target

The candidate test bank covers:

- exact snapshot round-trip;
- restart-stable genesis reload;
- active lease survival across restart;
- continued capacity exhaustion after restart;
- real outcome release after restart;
- stale CAS rejection across independent store connections;
- generation-skip rejection;
- snapshot tamper detection;
- head-metadata tamper detection;
- runner-capability drift rejection;
- idempotent initialization only for an identical state.

## Authority invariant

> Restart recovery restores known canonical state. It does not infer unknown physical state.

No new execution, verification, integration, or release authority is introduced by v0.0.5.
