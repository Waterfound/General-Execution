# v0.0.5 — Durable Head & Restart Recovery

## Goal

Keep the v0.0.4 capacity state consistent across coordinator restarts without guessing what happened to active provider work.

## Durable snapshot

A `DurableCapacitySnapshot` binds one replayable `RunnerCapacityState` to a `DurableCapacityHead` containing the runner identity, capability digest, generation, exact state digest, canonical payload digest, and optional previous durable-head digest.

Snapshots use canonical JSON. Loading reconstructs typed capacity transitions and replays the capacity state before admission. Capacity lease, release, transition, state, head, and snapshot schemas are version-strict.

## Head continuity

A later durable head must reference the exact previous head, advance generation, and contain a capacity-state prefix that reproduces the previous state digest. Checkpoints may therefore skip intermediate generations while preserving append-only continuity.

A caller can provide `expected_head_digest` during load or recovery. A different stored head is rejected. The persistence backend remains responsible for atomically maintaining one canonical head.

## Restart semantics

Recovery never guesses a provider outcome.

With no active leases, recovery status is `clean`.

With active leases, each lease returns as `RecoveredInFlightLease(status="in_flight_unknown")` and recovery status is `reconciliation_required`.

The restored `RunnerCapacityState` is unchanged. Recovered leases keep their original slots and continue to count against capacity until later provider evidence or explicit Session revocation produces the normal release transition.

## Module boundary

`durable_codec.py` owns typed capacity serialization. `durable.py` owns durable-head continuity and restart recovery. This keeps serialization independent from recovery policy.

## Conformance bank

The v0.0.5 tests cover deterministic round-trip, exact head reload, active-lease recovery, clean recovery after explicit release, outdated-head rejection, malformed payload rejection, schema-version rejection, wrong-runner rejection, successor continuity, backward-generation rejection, previous-head mismatch, deterministic serialization, and recovery-report consistency.

## Next boundary

After v0.0.5 is frozen, the next high-value milestone is a concrete persistence adapter that applies atomic canonical-head compare-and-swap and crash-safe replacement while preserving these protocol semantics.
